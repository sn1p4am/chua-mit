## 1. What GPUI and gpui-fast actually are

### 1.1 GPUI

GPUI is Zed Industries' GPU-accelerated Rust UI framework. Its frame model is documented precisely in the fork's own architecture doc:

- A frame walks the element tree three times — **request_layout** (views render into elements), **prepaint** (Taffy computes layout, elements are placed, hitboxes/listeners/dispatch nodes registered), **paint** (elements write primitives into the scene) — `<CHK>/docs/architecture.md:62-68`.
- Frame output is stored in flat, append-only arrays on the window's `Frame`; the window keeps two frames (on screen, being drawn) and swaps them — `<CHK>/docs/architecture.md:70-73`.
- Upstream has exactly one skip-work mechanism: an explicitly cached view (`AnyView::cached`) remembers its prepaint/paint index ranges and copies them when not notified and not moved (`Window::reuse_prepaint`, `Window::reuse_paint`) — `<CHK>/docs/architecture.md:75-79`.

Layout is Taffy, text on Windows is DirectWrite, rendering on Windows is Direct3D 11. Windows release binaries ship pre-compiled DXBC from `fxc.exe` at `vs_4_1`/`ps_4_1` (shader model 4.1) — `<CHK>/crates/gpui_windows/build.rs:23-70,149-174`.

### 1.2 What gpui-fast is

It is **not a rewrite and not a fork with a diverged API**. It is Zed's GPUI extracted into a standalone workspace with a `fast/` module tree bolted on through minimal hooks, and it advertises three things (`<CHK>/README.md:5-7`):

1. **Retained Mode** — unchanged views, layout nodes and text measurements are reused between frames.
2. **Scroll layers** — scrolled content is rasterized into cached GPU tiles and composited at the new offset.
3. **Window composition** — native content (WebView2 on Windows) embedded with GPUI menus/popovers/dialogs above it.

The self-imposed discipline is the important architectural fact, and it is enforced by CI:

- All fork logic lives in `crates/<crate>/src/fast/` — `<CHK>/AGENTS.md:6-9`.
- Upstream files hold only hooks: a field, a one-line call, a forwarding body, a visibility bump, a `#[path]` redirect — `<CHK>/AGENTS.md:10-13`.
- **"No new public API"**, and `script/check-upstream` must pass — `<CHK>/AGENTS.md:19`.
- The budget is mechanical: a hunk adding >8 lines, or a file adding >40 lines, or added lines that do not call into `fast/`, fail CI; exceptions are listed with a reason in `script/upstream-allowlist` — `<CHK>/docs/architecture.md:733-741`.
- Actual current divergence: **30 tracked files differ from upstream; the 20 in `crates/gpui/src` differ by +609/−776 lines** (more removed than added, because method bodies were replaced by calls into `fast/`) — `<CHK>/docs/architecture.md:737-741`.
- The only public-API addition is `Scene.layers` and the types it holds, needed by renderers — `<CHK>/docs/architecture.md:743-744`.

Importable units (`<CHK>/UPSTREAM:14-40`): `gpui`, `gpui_platform`, `gpui_macros`, `gpui_apple/linux/macos/windows/web/wgpu`, `collections`, `sum_tree`, `refineable`, `scheduler`, `util`, `zlog`, `ztracing`, `path`, `http_client`, `reqwest_client`, `bench_metrics`, `tooling/perf`. ### 1.3 Retained Mode — mechanism

A GPUI frame's elements are still rebuilt every frame by design; what gpui-fast retains is **frame work**, keyed by identity GPUI already has — `<CHK>/docs/architecture.md:23-39`, `140-153`:

- A view's record is found by its `GlobalElementId` (the `ElementId` path from the root, which includes `ElementId::View(entity_id)`), so retention follows exactly the identity upstream already uses for element state — `<CHK>/docs/architecture.md:140-148`.
- The id's hash is computed once and cached, but **equality still compares the full path**, so a hash collision cannot make one view reuse another's record — `<CHK>/docs/architecture.md:149-153`.
- Layout nodes are matched by a 64-bit key (hash of the path, with `uniform_list`/`list` items keyed by index so rows keep their layout while scrolling) — `<CHK>/docs/architecture.md:155-160`, `118-124`.
- A matched Taffy node is brought up to date before use: style fingerprint, exact child list, and measurement inputs are compared and only rewritten if different — this matters because Taffy dirties a node and all its ancestors on any `set_style`/`set_children`/`set_node_context` — `<CHK>/docs/architecture.md:385-396`.
- Text is the case where a naive implementation would dirty the tree every frame (a measured leaf holds a closure; a new closure dirties the node and every ancestor). gpui-fast does **carry** (same text+runs+style ⇒ take the old measurement) then **replay** (measure the new text under the same constraint sequence Taffy used; if every size matches, the node and all ancestors stay clean) — `<CHK>/docs/architecture.md:403-428`, `<CHK>/docs/retained-mode.md:128-141`.

**Five paths** a view can take per frame — Reused / Spliced / Built at retained layout / Prebuilt / Built — `<CHK>/docs/architecture.md:300-306`. "Spliced" is the interesting one: a view dirty only because something nested changed copies its output from the last frame in stretches around the rebuilt child — `<CHK>/docs/architecture.md:326-381`, implemented in `fast/splice.rs`.

**Dependency tracking is automatic and broader than upstream's notify contract** (`<CHK>/docs/retained-mode.md:24-52`):
- entities read (including read without observing), globals read (`cx.has_global::<G>()` depends on presence only), nested views, and `ListState`/`ScrollHandle` versions;
- ambient window input: `window.mouse_position()`, `window.modifiers()`, `window.capslock()` are recorded like a global read;
- an entity `update(..)`d **without** `notify` counts as changed for views inside a view notified since the last frame (upstream rebuilds exactly that set, since it rebuilds a notified view with everything under it).

**What the application must still do:** anything read outside entities/globals/list-or-scroll-state/window input — an `Rc<RefCell<..>>`, atomics, statics, wall-clock time, files, network state — is invisible to dependency tracking and needs an explicit `cx.notify()` — `<CHK>/docs/retained-mode.md:143-150`, `<CHK>/docs/architecture.md:590-616`. And a change made *every* frame (an entity notified, or a global written, during prepaint/paint, or on every frame) counts as changed even when the value is identical, which defeats retention for every view that read it — `<CHK>/docs/retained-mode.md:152-158`. This is the single biggest practical footgun, and the fork documents a concrete case: GPUI Kit writes window-wide state during render (`sync_focused_input_registry`, `GlobalState`, `SelectionStateRegistry`), which rebuilds ancestor views on every scrolled frame — `<CHK>/docs/scroll-layers.md:170-173`.

**Escape hatches:** `GPUI_VIEW_RETENTION=0` disables retention entirely (draws like upstream); `GPUI_SCROLL_LAYERS=0` disables scroll layers alone — `<CHK>/docs/architecture.md:289-293`.

### 1.4 Scroll layers

- Applies on **Windows/Direct3D 11**, macOS/Metal, Linux/wgpu; compiled out elsewhere (`fast::layers::COMPILED`) — `<CHK>/docs/scroll-layers.md:16-20`.
- A container gets a layer once it has scrolled on two consecutive frames, then takes one of three paths: **Composite** (only the offset moved → tiles drawn at the new offset, hitboxes/listeners/dispatch carried and translated), **Repaint** (content changed or scroll left the painted region → paint viewport + 2 viewports of overscan each side, hash tiles, re-rasterize only changed tiles), **Bypass** (draw exactly as without layers) — `<CHK>/docs/scroll-layers.md:51-73`.
- Bypass triggers include: background under the viewport is not one opaque solid quad; content has deferred/anchored elements, a focused input, or surfaces; content changed on ≥8 of the last 16 frames (demotion); paths covered by something drawn after them — `<CHK>/docs/scroll-layers.md:66-73`.
- Demotion backoff: first cooldown 60 stable frames, doubling per repeated demotion up to 1920 frames; updates during cooldown restart the full wait — `<CHK>/docs/scroll-layers.md:88-93`.
- **Lists get layers too**: `pub(crate) const LIST_LAYERS: bool = true;` — `<CHK>/crates/gpui/src/fast/layers/lists.rs:76`. (Note: `docs/architecture.md:583-588` still says list layers are off and "lists need per-row records for layers to pay off" — the flag was flipped after that prose was written. Treat the code as authoritative and the doc sentence as stale.) A list's layer holds the viewport plus two viewports of rows each side, each row kept apart; a scrolled frame renders only rows entering the overscan, rows whose hover changed, and rows showing again — `<CHK>/docs/scroll-layers.md:28-44`.
- **Tile budget is 64 MiB per window**: `const TILE_BUDGET_BYTES: u64 = 64 << 20;` — `<CHK>/crates/gpui/src/fast/layers/policy.rs:57`, LRU-evicted — `<CHK>/docs/architecture.md:685-686`.

GPUI Kit's Button story, 145 Hz, one wheel event per frame (`<CHK>/docs/scroll-layers.md:157-165`): process CPU 23–41 % (mostly 26–33 %) without layers vs 17–30 % (mostly 18–22 %) with; main-thread draw 1.26–2.38 ms vs 0.83–1.73 ms. 89 % of scrolled frames were composited, the rest repaints as the scroll crossed the overscan.

Costs the fork itself admits (`<CHK>/docs/architecture.md:671-692`): reusing a subtree copies its ranges (linear in the reused size, "not free"); a frame that repaints a layer paints five viewports of content and costs "up to 5–6.5 ms against 0.6 ms"; the layer hooks cost +0.85 % instructions on average across headless scenarios, at most +2.7 %.

**Verification is genuine, not marketing.** The correctness oracle drives two windows through the same random history, one incremental and one drawing from scratch, and requires the complete scene (layers, shadows, quads, underlines, monochrome/subpixel/polychrome sprites with orderings, paths) and every hitbox with bounds, content mask and behavior to match — and asserts that the incremental window actually reused layout nodes and subtrees so it cannot pass by retaining nothing — `<CHK>/docs/architecture.md:632-646`. There is also a layer oracle over random wheel/hover/click/key/content histories comparing expanded scenes and listener-observed positions (`<CHK>/docs/scroll-layers.md:120-137`), and renderer pixel tests for Windows layers that run "on a hardware device or WARP" — `<CHK>/docs/scroll-layers.md:133-135`.

### 1.6 What the fork does *not* change

It does not add a `Component` trait, does not restructure the public API, and requires no application changes beyond the notify rule cached views already impose (`<CHK>/docs/architecture.md:51-54`). Concretely: code written for upstream GPUI compiles unchanged.

Compare this to what **upstream Zed is doing in parallel**: PR #63800 (Mikayla Maki) is a persistent `SlotMap<ViewNodeId, ViewNode>` view tree, a new public `Component` trait, `View` sealed, +9,212/−1,256 across 48 files — and as of the article's writing it is **still off `main` on a draft branch**, with half a dozen preparatory PRs landed first ([gpui-archipelago, "The Retained Frame"](https://gpui-archipelago.github.io/news/the-retained-frame/)). So the two retained-rendering designs are not converging soon, and a product that picks gpui-fast picks the fork's mechanism over upstream's future one.

### 2.1 Visually minimal and refined — Pass (with GPUI Kit / gpui-component)

There is no theme, no widget set and no icon set in GPUI itself: a button is a `div` with styling. What makes this a pass is the ecosystem layer, which is mature by the standards of this niche.

`gpui-kit` 0.7.1 / `gpui-component` 0.7.1 (Apache-2.0, Longbridge) advertises 75+ documented components, AccessKit accessibility, UI integration testing, data tables with virtual scrolling and resizable columns "across hundreds of thousands of rows", virtual lists including variable-height items, built-in charts, dock layout, i18n, and "used to build Longbridge Pro from day one" ([longbridge/gpui-kit README](https://github.com/longbridge/gpui-kit)).

The file tree confirms the download-manager-relevant parts exist: `crates/component/src/table/{data_table,column,delegate,state,loading}.rs`, `crates/component/src/list/{list,delegate,cache,loading,separator_item}.rs`, `crates/component/src/virtual_list.rs`, `crates/component/src/progress/{progress,progress_circle}.rs`, `crates/component/src/chart/{area,bar,line,pie,radar,sankey,candlestick}_chart.rs`, `crates/component/src/plot/`, `crates/component/locales/ui.yml` (i18n), `crates/component/src/menu/{app_menu_bar,context_menu,dropdown_menu,popup_menu}.rs`, `crates/component/src/native_menu/windows.rs` (verified via the GitHub tree API for `longbridge/gpui-kit@main`).

A speed graph is a `line_chart` or `area_chart`; a task list is `data_table`/`list`; progress is `progress`; settings is forms; the tray menu is `muda`/`tray-icon` (see 6.4). **Verdict: pass, provided you accept gpui-component as a dependency — which you were going to anyway (see §5).**

### 2.2a Cold start to first painted window — Conditional, undocumented

**No number exists.** Neither the checkout, the fork's docs, Zed's docs nor the crates.io metadata publishes a cold-start or time-to-first-frame measurement. I am not going to invent one. What can be stated is the *shape* of the startup cost, from source:

1. `DirectXDevices::new()` — DXGI factory, adapter enumeration, `D3D11CreateDevice`, feature-support query — `<CHK>/crates/gpui_windows/src/directx_devices.rs:47-72,106-193`.
2. `DirectWriteTextSystem::new(...)` runs **synchronously in platform construction**: creates the DWrite factory, registers an in-memory font-file loader, creates a font-set builder, resolves the locale via `GetUserDefaultLocaleName`, and calls `GetSystemFontCollection(false, &mut result, true)` — the third argument (`checkForUpdates = true`) forces a font-cache check — `<CHK>/crates/gpui_windows/src/direct_write.rs:175-208`, `<CHK>/crates/gpui_windows/src/platform.rs:180-270`.
3. `attach_gpu()` then panics-hard on failure and starts the vsync thread — `<CHK>/crates/gpui_windows/src/platform.rs:405-418`.
4. A first frame must be drawn and presented before anything is on screen.

**Fork-specific startup risk, and it is concrete.** The released Windows binary compiles HLSL at **build time** with `fxc.exe`, located by probing `where.exe fxc.exe` and then the newest Windows SDK under `HKLM\SOFTWARE\WOW6432Node\Microsoft\Microsoft SDKs\Windows\v10.0`, and **panics with "Failed to find fxc.exe"** if it is absent — `<CHK>/crates/gpui_windows/build.rs:73-141`. That is a build-machine requirement, not a user-facing one (users get pre-compiled DXBC in the binary), but it means a Windows CI runner must have the Windows SDK, and it is the kind of thing that breaks a fresh contributor or a container build. The fork's own commit log carries a fix in this area: "ci: allow release dependency tests time to compile on Windows (#53)" (2026-10-09).

Two favourable facts: the checkout already includes upstream's "Improve Zed's startup time (#65170)" and "Reduce the dependency footprint (#65176)" (both synced 2026-10-05, visible in `<CHK>` git log), and segment heap is enabled in the manifest, which is a documented Windows memory/startup win — see 6.5.

Realistically, a D3D11 + DirectWrite app that opens one small window has a startup budget dominated by process load, D3D device creation (~tens of ms on a warm driver) and font collection init. Whether the total lands under 300 ms on the target hardware class **cannot be answered from any published source**; it must be measured (§5, experiment E1).

### 2.2b Idle cost while sitting in the tray for hours — Conditional

This is the requirement where the source is unusually explicit, so here is the mechanism end to end.

- **Drawing is event-driven, not continuous.** In the frame callback, `let should_draw = invalidator.is_dirty() || force_render; if should_draw { ... window.draw(cx) ... } else if needs_present { window.present() }` — `<CHK>/crates/gpui/src/window.rs:1897-1917`. An idle, clean window does **not** run the element tree, layout, text shaping or paint.
- **But a frame request arrives every vsync regardless.** `begin_vsync_thread` spawns a thread that, in a loop, calls `VSyncProvider::wait_for_vsync()` (`DwmFlush()`) and then, for **every** registered window, `RedrawWindow(hwnd, None, None, RDW_INVALIDATE)` — `<CHK>/crates/gpui_windows/src/platform.rs:433-495`, `<CHK>/crates/gpui_windows/src/vsync.rs:31-59`.
- `WM_PAINT` reaches `draw_window`, which calls the GPUI frame callback with `require_presentation: false, force_render: false` — `<CHK>/crates/gpui_windows/src/events.rs:1330-1381`.
- The callback then **returns early** at `should_draw == false`, so the per-frame cost is: one repaint invalidation, one `WM_PAINT`, one callback invocation, one `IsIconic`/visibility check, and a scheduler wakeup. The frame is skipped and, in profiler builds, recorded as `FrameSkipReason::NoRenderNeeded` — `<CHK>/crates/gpui/src/window.rs:1937-1944`.
- **Hidden windows are cheaper still**: while `IsWindowVisible(hwnd)` is false the vsync thread explicitly *discards* the frame signal rather than recording it ("Hidden windows may not consume WM_PAINT until shown again") — `<CHK>/crates/gpui_windows/src/platform.rs:477-489`. And on `WM_SIZE` with `SIZE_MINIMIZED` the window **takes away its own frame callback**, so no frame callback runs at all while minimized — `<CHK>/crates/gpui_windows/src/events.rs:244-263`.
- **Throttling exists for inactive (not minimized) windows**: `inactive_frame_interval: Some(Duration::from_micros(33_333))` = 30 fps cap when the window is not active and input is not high-rate; thermal Serious/Critical caps at ~60 fps — `<CHK>/crates/gpui/src/platform.rs:2640`, `<CHK>/crates/gpui/src/window.rs:1829-1876`. Note the condition ordering: a request that carries a *pending animation frame callback* is exempt from the inactivity cap (`min_frame_interval = None` when `!require_presentation && next_frame_callbacks.is_empty()` is false) — so any `request_animation_frame` driving a spinner keeps the window at full refresh while unfocused.
- **The GPU context is retained.** `attach_gpu` stores the `ID3D11Device`/context in platform state and `begin_vsync_thread` clones it; it is released only by `detach_gpu()`, which is called when the platform switches to headless or on window-mode change — `<CHK>/crates/gpui_windows/src/platform.rs:405-431,618-646`. Hiding to the tray is *not* a switch to headless, so a tray-resident app keeps the D3D device, the DXGI factory and the adapter alive, and keeps the vsync thread waking at the monitor's refresh rate (60–165 Hz) forever.
- There **is** an application-reachable way out: `App::request_windowing(WindowingRequest::Headless)` → `detach_gpu()` stops the vsync thread and drops the devices — `<CHK>/crates/gpui/src/app.rs:1177`, `<CHK>/crates/gpui_windows/src/platform.rs:628-646`. Windows cannot be opened while headless (`<CHK>/crates/gpui_windows/src/platform.rs:759`), so this is usable for "hidden in tray, no UI open" and must be reversed with `WindowingRequest::Windowed` before showing anything. Note also that closing/destroying windows may itself be a route back to headless; the platform's `WindowingRequest` machinery is what an app should build on.

**What is documented vs not.** The +0.85 % instruction overhead of the layer hooks and the 0.19 ms/present-frame cost of an unchanged window are documented (`<CHK>/docs/architecture.md:691-692`, `<CHK>/README.md:15`). The **idle** cost — a `DwmFlush` wait plus one invalidation, one `WM_PAINT` and one callback per window per refresh, at 60–165 Hz, for hours — is **not measured anywhere public**. Nobody publishes "GPUI tray app, 8 hours, % of a core, battery drain". The mechanism says it is small; "small" is not a number, and its effect on package C-states / laptop battery is exactly the kind of thing that only an on-device measurement settles (experiment E2).

### 2.3c Smooth scrolling and live progress with thousands of rows — Pass

Two virtual-list APIs exist, both in `crates/gpui/src/elements/`:

**`uniform_list`** (fixed row height) — `pub fn uniform_list<R>(...)` at `<CHK>/crates/gpui/src/elements/uniform_list.rs:22`; state is a `UniformListScrollHandle` with `scroll_to_item`, `scroll_to_item_strict`, `scroll_to_item_with_offset`, `scroll_to_bottom`, `logical_scroll_top_index`, `y_flipped`, and builder options `with_width_from_item`, `with_sizing_behavior`, `with_horizontal_sizing_behavior`, `with_decoration`, `track_scroll` — `<CHK>/crates/gpui/src/elements/uniform_list.rs:134-260,662-756`.

**`ListState`** (variable row height, backed by a `SumTree<ListItem>` of measured heights) — `<CHK>/crates/gpui/src/elements/list.rs:24-34,54-77`. The API that matters for a download manager is unusually well suited:

- `ListState::new(item_count, alignment, overdraw)` — overdraw is extra space rendered and measured above/below the viewport to prevent flicker/pop-in while scrolling — `<CHK>/crates/gpui/src/elements/list.rs:308-333`.
- **`with_uniform_item_height(height)`** — pre-populates every unmeasured item with a height hint so the scrollbar thumb is correctly sized from the first frame, without measuring all items; real heights replace the hint as rows render. The doc comment names the exact use case: *"a cheaper alternative to `measure_all` for lists where items have roughly uniform heights (e.g. table rows)"* — `<CHK>/crates/gpui/src/elements/list.rs:343-352`. For 5k–50k download rows this is the right call.
- `splice(old_range, count)` for updating the model when rows are added/removed or change height — `<CHK>/crates/gpui/src/elements/list.rs:509`; `reset`, `reset_with_uniform_height`, `remeasure`, `remeasure_items(range)` for partial invalidation — `<CHK>/crates/gpui/src/elements/list.rs:357-425`.
- Follow-the-tail behaviour is first-class, which is exactly what a download list wants: `set_follow_mode`, `pause_following_tail`, `is_following_tail`, `is_scrolled_to_end`, `scroll_to_end` — `<CHK>/crates/gpui/src/elements/list.rs:489,612-672`.
- Scrollbar plumbing for a custom-drawn scrollbar: `scrollbar_drag_started/ended`, `is_scrollbar_dragging`, `set_offset_from_scrollbar`, `max_offset_for_scrollbar`, `scroll_px_offset_for_scrollbar`, `viewport_bounds`, `item_is_above/below_viewport`, `bounds_for_item` — `<CHK>/crates/gpui/src/elements/list.rs:726-855`.

**Partial row updates are handled at two levels.** (a) `ListState` carries a `StateVersion` bumped whenever its state changes, so a view that read it is redrawn when it moves "whether anything was notified or not" — `<CHK>/crates/gpui/src/elements/list.rs:76`, `<CHK>/docs/architecture.md:220-223`. (b) Retained Mode: only the view that changed is rebuilt, and if it is nested inside an otherwise-clean view, the parent's output is spliced around it (`fast/splice.rs`). A ticking progress percentage inside one row changes that row only; the parent list is not rebuilt.

**Scroll layers make the scroll itself cheap and this is Windows-specific:** `LIST_LAYERS = true` (`<CHK>/crates/gpui/src/fast/layers/lists.rs:76`) and scroll layers are compiled in for Direct3D 11 (`<CHK>/docs/scroll-layers.md:16-20`). A scrolled list frame renders only the rows entering the overscan, the rows whose hover changed, and the rows re-appearing; every other row's hitboxes/listeners/element states are carried from the last frame with hitboxes translated by the scroll — `<CHK>/docs/scroll-layers.md:28-44`. Measured: `scroll-uniform-list` 0.397 ms → 0.137 ms, `scroll-list` 0.377 ms → 0.147 ms (`<CHK>/docs/scroll-layers.md:144-149`).

The one thing to watch is the documented exception: **a list row that contains a focused text input forces Bypass** (as does deferred/anchored content and non-solid backgrounds) — `<CHK>/docs/scroll-layers.md:66-73`, `<CHK>/docs/architecture.md:559-560`. A search box *inside* a scrolled list would defeat compositing; a search box above the list does not.

**Verdict: pass, and this is GPUI's strongest area relative to the alternatives.** No other Rust option in §3 offers retained per-row output plus GPU-tile scroll compositing on Windows.

### 2.4d Memory footprint with 5k–50k rows — Conditional, undocumented for Windows

What is knowable:

- `ListState` holds a `SumTree<ListItem>` — one measured height per row, plus whatever the row's element state holds. It does **not** hold rendered rows; only the viewport plus overscan is built. So 5k vs 50k rows differ by a sum-tree of `usize`-sized heights, i.e. tens to hundreds of KB, not by a proportional render cost. That is an inference from the data structure (`<CHK>/crates/gpui/src/elements/list.rs:62-77`, `<CHK>/docs/retained-mode.md:112-126`), not a measurement.
- Per-row *element state* is retained only for rows the list is showing; a row leaving the viewport loses its element states and is rendered afresh before it shows again (`<CHK>/docs/scroll-layers.md:36-40`) — so scroll position of a nested scroller inside a row is dropped, and memory does not accumulate per scrolled-past row.
- **Known bounded cost: 64 MiB of tile textures per window** (`<CHK>/crates/gpui/src/fast/layers/policy.rs:57`), LRU-evicted (`<CHK>/docs/architecture.md:685-686`). Plus the frame records ("proportional to what is on screen" — `<CHK>/docs/architecture.md:673-675`) and the retained Taffy tree.
- The fork's benchmark tooling can sample resident memory — **but not on Windows**: `resident_memory()` is implemented for macOS (`phys_footprint`) and Linux (`/proc/self/statm`) and returns `None` for every other platform, i.e. Windows — `<CHK>/crates/gpui_perf/src/showcase/metrics.rs:371-393`. So the fork's own showcase will print `-` for memory on Windows (`<CHK>/crates/gpui_perf/src/showcase/auto.rs:352-353`).

**No public number exists for RSS with 5k or 50k rows on Windows, for GPUI or for any alternative in §3.** Anything quoted would be invention. This must be measured (experiment E3). My expectation, stated as an expectation and not a finding: a retained virtual list's memory is dominated by the GPU atlas, the tile budget and the frame's flat arrays, not by row count — so 5k→50k should be close to flat. The 64 MiB tile budget is the number to watch, and it is per window, not per row.

### 2.3 Windows rendering backend, driver/GPU compatibility, fallback — Conditional

**Backend: Direct3D 11, unambiguously.** `DirectXDevices::new()` creates a DXGI factory (`CreateDXGIFactory2`) and enumerates adapters with `EnumAdapters`, creating an `ID3D11Device` per adapter until one succeeds — `<CHK>/crates/gpui_windows/src/directx_devices.rs:47-72,106-140`.

- **Feature levels requested, in order: `D3D_FEATURE_LEVEL_11_1`, `11_0`, then `10_1`** — `<CHK>/crates/gpui_windows/src/directx_devices.rs:160-167`. Only those three are handled; anything else hits `_ => unreachable!()` in the logging match — `<CHK>/crates/gpui_windows/src/directx_devices.rs:53-64`.
- **A hard capability gate**: after device creation it queries `D3D11_FEATURE_D3D10_X_HARDWARE_OPTIONS` and **rejects the device** unless `ComputeShaders_Plus_RawAndStructuredBuffers_Via_Shader_4_x` is true, with the error "Required feature StructuredBuffer is not supported by GPU/driver" — `<CHK>/crates/gpui_windows/src/directx_devices.rs:174-193`. This is the real minimum: a D3D11 device with SM4.x structured buffers.
- Shaders are SM 4.1 (`vs_4_1`/`ps_4_1`) — `<CHK>/crates/gpui_windows/build.rs:159,172`. Note `D3D11_CREATE_DEVICE_BGRA_SUPPORT` is always set, `D3D11_CREATE_DEVICE_DEBUG` only in debug builds when the debug layer is present — `<CHK>/crates/gpui_windows/src/directx_devices.rs:76-89,150-154`.
- Device-lost recovery exists: `try_to_recover_from_device_lost` retries up to 5 times with a 100 ms+ backoff — `<CHK>/crates/gpui_windows/src/directx_devices.rs:24-36`; and the vsync thread polls `check_device_lost(device)` every frame and calls `handle_gpu_device_lost`, **panicking with "Device lost: {err}" if recovery fails** — `<CHK>/crates/gpui_windows/src/platform.rs:459-471`.

**What this means for the Chinese market specifically.**

- **Old Intel iGPUs**: the requirement is D3D11 FL10.1 + structured buffers, which is Sandy Bridge (2011) / Ivy Bridge (2012) HD 2000/3000/4000 territory for the *API*, but Intel's D3D11 Windows drivers for those parts are effectively frozen. Zed's own published hardware requirement is "A GPU that supports DirectX 11 (most PCs from 2012+)" **and** "Current NVIDIA/AMD/Intel/Qualcomm driver (**not the Microsoft Basic Display Adapter**)" — [zed.dev/docs/installation](https://zed.dev/docs/installation). The second clause is the binding one for old hardware: a machine that has silently fallen back to the Microsoft Basic Display Adapter (very common on old Chinese OEM machines and after a botched driver update) has no usable D3D11 device.
- **Compared to the alternatives, this is still the *broadest* requirement.** wgpu (egui's `egui-wgpu`, iced's `iced_wgpu`, and gpui_wgpu for the web path) supports **Vulkan, DX12 and OpenGL 3.3+** on Windows and has **no D3D11 backend at all** ([wgpu README](https://github.com/gfx-rs/wgpu)) — DX12 is Windows 10 + a 2015-ish GPU, Vulkan on Windows means a modern vendor driver, and GL 3.3 is downlevel/best-effort. GPUI's FL10.1 D3D11 target reaches further back than any wgpu-based option, and much further back than WinUI 3 (Windows App SDK) or WebView2-with-GPU.
- **VMs / RDP / GPU-less hosts**: this is where GPUI is weakest.
  - Adapter enumeration is plain `EnumAdapters` with **no `EnumAdapterByGpuPreference`** — `<CHK>/crates/gpui_windows/src/directx_devices.rs:115-116`. GPUI never asks for a specific power preference, so it takes the first adapter that satisfies the capability check.
  - **There is no explicit WARP/software path, and the failure mode is a panic.** `attach_gpu()` calls `.unwrap_or_else(|error| panic!("failed to initialize DirectX: {error:#}"))` — `<CHK>/crates/gpui_windows/src/platform.rs:405-406`. `get_adapter` loops `for adapter_index in 0..` and ends in `unreachable!()` if no adapter ever yields a capable device — `<CHK>/crates/gpui_windows/src/directx_devices.rs:115-139`.
  - In practice a GPU-less VM or an RDP session will usually still enumerate an adapter (Microsoft Basic Render Driver / WARP is enumerable and does support FL11_0 + structured buffers), so the app will typically start and be *slow* rather than fail. Zed's docs say the same thing in prose: *"If you're running Zed inside a virtual machine, it will use the emulated adapter provided by your VM. While Zed will work in this environment, performance may be degraded."* — [zed.dev/docs/windows](https://zed.dev/docs/windows). But note the polarity: that sentence assumes an emulated adapter exists. On a host where the Basic Display Adapter is present but not enumerable as a capable D3D11 device, the code path above is a **startup panic**, not a degraded window.
  - The fork's own Windows layer tests run "on a hardware device or WARP" (`<CHK>/docs/scroll-layers.md:133-135`), which confirms WARP is at least a tested configuration for tile compositing.
- **Fallback story: none.** There is no GL/software fallback to fall back *to*. If D3D11 is unavailable the process panics on startup. For a consumer download manager shipped into an unmanaged Chinese install base, that is a support-ticket generator unless the app itself preflights with `dxdiag`-equivalent checks (create a throwaway FL10_1 device and check the structured-buffer flag) and shows a native Win32 fallback window when it fails.
- On the plus side for this market: **D3D11 is ubiquitous and well understood by Chinese OEM drivers**, and there is no DXIL/DXC runtime dependency — shaders are pre-compiled DXBC embedded in the binary (`<CHK>/crates/gpui_windows/build.rs:143-240`), so no `dxcompiler.dll` to ship or to be missing.

### 2.4 Chinese text and Windows IME — Conditional

**Text rendering is DirectWrite, and it is the good path.** The platform creates a `DirectWriteTextSystem` (`<CHK>/crates/gpui_windows/src/direct_write.rs:175-222`) and implements `PlatformTextSystem` on it — `add_fonts`, `all_font_names`, `font_id`, `font_metrics`, `typographic_bounds`, `advance`, `glyph_for_char`, `glyph_raster_bounds`, `rasterize_glyph`, `layout_line` (`<CHK>/crates/gpui_windows/src/direct_write.rs:236-294`). Line layout goes through `IDWriteTextFormat1` + `IDWriteFactory5::CreateTextLayout` — `<CHK>/crates/gpui_windows/src/direct_write.rs:548-569`.

**CJK font fallback is the OS's own, by construction.**
- When the app configures no fallbacks, `IDWriteTextFormat1::SetFontFallback` is simply never called, and DirectWrite's `IDWriteTextLayout` performs its own system fallback per run — `<CHK>/crates/gpui_windows/src/direct_write.rs:560-569` and `font_info.fallbacks = None` at `<CHK>/crates/gpui_windows/src/direct_write.rs:1792`. This is the same fallback pipeline every native Windows app and every browser on Windows uses, so Chinese glyph coverage and full-width punctuation behaviour are as good as Windows itself.
- When the app *does* want control, `FontFallbacks` is a public, serde/schemars-derivable list of family names (`<CHK>/crates/gpui/src/text_system/font_fallbacks.rs:6-21`), styled via `.font_fallbacks(...)` (`<CHK>/crates/gpui/src/styled.rs:734`, `TextStyle.font_fallbacks` at `<CHK>/crates/gpui/src/style.rs:449`). On Windows it is compiled into a real `IDWriteFontFallbackBuilder`: for each configured family it looks up matching fonts, reads `IDWriteFontFace::GetUnicodeRanges`, and adds an explicit Unicode-range mapping; then it **chains the system fallback underneath** via `factory.GetSystemFontFallback()` + `builder.AddMappings(...)` — `<CHK>/crates/gpui_windows/src/direct_write.rs:398-454`. That is the correct design: your choice first, OS fallback for everything else. Concretely, `.font_fallbacks(["Microsoft YaHei UI", "Noto Sans SC"])` gives you exactly the Chinese rendering you asked for and does not regress Latin text.
- **The default UI font is read from the OS, not hardcoded.** `get_system_ui_font_name()` calls `SystemParametersInfoW(SPI_GETICONTITLELOGFONT, ...)` and uses the returned `lfFaceName`, falling back to the literal `"Segoe UI"` only if the API fails — `<CHK>/crates/gpui_windows/src/direct_write.rs:1899-1921`. On a Simplified-Chinese Windows install that returns the shell's icon-title font (Microsoft YaHei UI in practice), so the default UI font is already the locale's native UI font. The `".SystemUIFont"` sentinel maps onto it (`<CHK>/crates/gpui/src/text_system.rs:1280,1410,1427`).
- Localized font *family* names are resolved against the user's locale with an `en-US` retry — `get_name()` tries `FindLocaleName(locale)` then `DEFAULT_LOCALE_NAME = "en-US"` — `<CHK>/crates/gpui_windows/src/direct_write.rs:1858-1876,1961`. Good for "微软雅黑" vs "Microsoft YaHei" style variance.

None of those is a fundamental "CJK does not work" problem, and #64832 and #49860 are editor-font-specific. Treat CJK *text* as a pass and budget for polish work.

**IME is implemented properly, and this is the part most frameworks get wrong.** `gpui_windows` handles `WM_IME_STARTCOMPOSITION` and `WM_IME_COMPOSITION` — `<CHK>/crates/gpui_windows/src/events.rs:156-157` — and:

- **Composition window and candidate window are both positioned at the text caret.** `update_ime_position` calls `ImmSetCompositionWindow` with `CFS_POINT` at the caret point and `ImmSetCandidateWindow` with `CANDIDATEFORM { dwStyle: CFS_CANDIDATEPOS, ptCurrentPos: caret }` — `<CHK>/crates/gpui_windows/src/events.rs:670-697`. The caret point comes from `retrieve_caret_position`, which scales to device pixels and takes the **vertical middle** of the caret box (`y = origin.y + height/2`) — `<CHK>/crates/gpui_windows/src/events.rs:655-661`, and the platform forwards `update_ime_position(bounds)` from the window — `<CHK>/crates/gpui_windows/src/window.rs:1075-1083`.
- **Commit vs pre-edit is correctly distinguished.** `GCS_RESULTSTR` → `replace_text_in_range(None, ...)`; `GCS_COMPSTR` → `replace_and_mark_text_in_range(None, ..., caret_range)` so the composition is *marked* (composition underline) rather than inserted — `<CHK>/crates/gpui_windows/src/events.rs:744-777`. `GCS_CURSORPOS` and `GCS_COMPATTR` are read, and the composition cursor position is only trusted when it is adjacent to `ATTR_INPUT` (unconverted) text — `<CHK>/crates/gpui_windows/src/events.rs:1720-1752`.
- **The `lparam == 0` case is handled** with the documented Japanese-IME caveat ("Japanese IME may send this message with lparam = 0, which indicates that there is no composition string") — `<CHK>/crates/gpui_windows/src/events.rs:736-742`.
- **IME is enabled/disabled per focus**, via `ImmAssociateContextEx(handle, HIMC::default(), IACE_DEFAULT)` vs `... 0`, with an explicit guard that a *different* window's composition is not committed when this window's text-input state changes (the IME context is per-thread, not per-window) — `<CHK>/crates/gpui_windows/src/events.rs:699-727`. `update_ime_enabled` is called from `draw_window` — `<CHK>/crates/gpui_windows/src/events.rs:1377`.
- Unicode surrogate pairs from `WM_CHAR` are reassembled — `<CHK>/crates/gpui_windows/src/events.rs:1384-1394`.
- The `windows` crate feature list includes `Win32_UI_Input_Ime` for both `gpui` and `gpui_windows` — `<CHK>/Cargo.toml:363`, `<CHK>/crates/gpui_windows/Cargo.toml:60`.

**But there is a real, still-open bug that affects every IME on Windows, Chinese included.** `retrieve_caret_position` returns a single point at the *vertical middle* of the caret line and `update_ime_position` passes it with `CFS_CANDIDATEPOS`, which carries no exclusion area. Issue [#64850](https://github.com/zed-industries/zed/issues/64850) (open, 2026-09-28) documents the consequences: when there is not enough room below the caret, the IME flips the candidate window above it and the bottom edge lands on the middle of the input line, covering the composition text — you cannot see what you are typing while composing. The reporter's analysis names the exact lines in `gpui_windows/src/events.rs` and proposes `CFS_EXCLUDE` with `rcArea` set to the caret rectangle instead. The reporter also notes the editor has the same misplacement with an offset that varies with vertical screen position.

- The fork has already diverged in a way that complicates merges: commit "gpui: lay out with **Taffy 0.14**, whose cache keeps clean subtrees laid out (#49)" — while this checkout's workspace pins `taffy = { version = "=0.13.0" }` (`<CHK>/Cargo.toml:49`). - The ecosystem's recent history is a public fight, documented in detail at [gpui-archipelago, "The 315-Day Vacuum"](https://gpui-archipelago.github.io/news/315-day-vacuum/): 315 days without a crates.io release, 523 commits piled up upstream, a public 24-hour ultimatum, then Longbridge republishing Zed's GPUI under the `gpui-pre-*` names; the earlier community mirror `gpui-unofficial` was closed as "not planned" and a PR switching to it rejected with a one-word "No!"; the `gpui-component` → `gpui-kit` rebrand collided with an existing third-party `gpuikit` repo. Zed's official account responded with a commitment to automate crates.io publishing "by the end of the month" — **and as of 2026-10-12 the newest official `gpui` is still 0.2.2 from 2025-10-22**, so that commitment has not yet shown up as an artifact. (Treat this source as a community write-up, not an official record; the crates.io numbers above independently corroborate the "no official release" part.)
- **Upstream is building a competing retained-rendering design** (#63800, persistent view tree with a new public `Component` trait) that is still off `main`. If it lands, the `fast/` hook architecture has to survive it.

**The `gpui-pre` / `gpui-kit` coupling is explicit and consequential.** `gpui-kit` pins the exact snapshot with an inline explanation of why carets were abandoned: *"GPUI comes from the `gpui-pre-*` snapshots of Zed's crates, and any snapshot may change GPUI's API. These requirements are what the published gpui-kit crates carry to crates.io, so they pin the exact snapshot the release was built against: **a caret requirement let the weekly release move applications onto a newer snapshot that gpui-component did not compile with (#3156)**. Bump every snapshot crate together with its Cargo.lock entry; `script/check-gpui-pin.ts` fails CI when a pin is not exact."* — [longbridge/gpui-kit Cargo.toml](https://github.com/longbridge/gpui-kit/blob/main/Cargo.toml).

That is the whole risk in one paragraph: **the UI library you would depend on pins `=0.3.8` while crates.io already has 0.3.9**, and a caret range previously broke compilation. Meanwhile `gpui-fast`'s own compat crates are pinned to `=0.3.8` too (`<CHK>/compat/gpui-pre/Cargo.toml:3`, `<CHK>/compat/README.md:26-28`), and gpui-kit's `gpui-fast` feature — the flag that selects the fork instead of the snapshot — is pinned to `gpui-fast = "0.1.3"` in the workspace even though 0.1.6 is published.

**What "pin to a git rev" costs over 1–2 years, concretely.** Pinning `gpui-fast` to a rev buys reproducibility at these prices:

1. **Every dependency of the pinned rev is frozen too.** Cargo resolves the git rev's workspace; a `[patch.crates-io]` for `gpui-pre-*`, or the `gpui-fast` feature of `gpui-kit`, drags the whole graph. You cannot take a security fix in `reqwest`/`rustls` without either a compatible bump or re-pinning the fork.
2. **Upstream security and correctness fixes stop arriving.** GPUI's Windows layer has active bug-fixing (candidate-window IME fixes, device-loss recovery, DPI bugs). On a pinned rev you inherit them only by upgrading.
3. **The upgrade is not a version bump, it is a rebase-verification exercise.** Each upgrade moves the target commit by weeks of Zed churn; the fork's own docs describe the work (`docs/upstream-sync.md`) and the fork itself is 5 days behind at any moment.
4. **You become the maintainer of the fork for your own purposes.** If you need a fix in `gpui_windows`, you either wait for sunli829/huacnlee or you carry a patch — and carrying patches means keeping a fork of a fork in sync with a fork.
5. **Cargo footguns.** `[patch.crates-io]` only replaces a package with the same name *and* a version meeting the requirement; the compat README itself warns that when GPUI Kit moves to a newer `gpui-pre`, "Cargo warns that the patch was not used and keeps the snapshot" (`<CHK>/compat/README.md:26-28`). Silent non-application of a patch is a nasty failure mode — you think you are running gpui-fast and you are running the snapshot.
6. **The `gpui-pre` → `gpui_kit::` path rewrite.** `gpui-pre` rewrites the `gpui::` paths its macros emit to `::gpui_kit::`; gpui-fast's macros do not, so a crate depending on GPUI Kit alone must alias at its root with `extern crate gpui_kit as gpui;` — `<CHK>/compat/README.md:29-31`. This is a macro-hygiene mismatch that leaks into your crate root.

Mitigating facts, stated fairly: the fork is technically disciplined (CI-enforced hook budgets, oracles, `script/check-upstream`), it does sync upstream regularly, it has a release workflow, and the component layer above it (`gpui-kit`/`gpui-component`, Apache-2.0) is genuinely production-exercised (Longbridge Pro) with an active i18n and a Chinese-language documentation set. The instability is in the *engine distribution*, not in the component library's competence.

**Verdict: fail as a "depend on crates.io and take updates" story; conditionally acceptable only if you (a) pin a git rev, (b) own the upgrade cadence, and (c) accept that a breaking snapshot is a rebase, not a `cargo update`.**

### 2.6 Packaging — Conditional

**Binary size.** No public number exists for a minimal GPUI app on Windows. The only data point is the full editor: **`Zed-x86_64.exe` = 84,005,568 bytes (80.1 MiB)**, released 2026-09-30 as v1.22.0 (GitHub releases API; 122,127 downloads). That bundles the whole editor — tree-sitter grammars, LSP plumbing, extensions host, themes, AI client. It is an upper bound and not an estimate. A minimal gpui + gpui-component app that excludes tree-sitter, markdown, HTML and the editor would be far smaller, but I will not guess by how much. (`gpui-kit`'s default features pull the Lucide icon set as `gpui-kit-assets`; most `tree-sitter-*` features are optional and off by default — [gpui-kit Cargo.toml](https://github.com/longbridge/gpui-kit/blob/main/crates/kit/Cargo.toml).)

**Installer story.** Zed ships a single `.exe` installer plus an MSI path and `winget install -e --id ZedIndustries.Zed` — [zed.dev/docs/windows](https://zed.dev/docs/windows). Tauri's bundler (NSIS + WiX MSI + built-in updater) is the mature Rust answer if you want it, and it is MIT/Apache-2.0 and usable independently of whether you use Tauri's webview. GPUI gives you nothing here: you would pair the binary with NSIS/WiX or Tauri's bundler yourself.

**Code signing.** Nothing GPUI-specific; it is a Windows problem for everyone. For mainland China the practical points are: an OV certificate already triggers SmartScreen reputation-building, an **EV certificate gives immediate SmartScreen trust**, and a Chinese CA (WoSign/CFCA/TrustAsia etc.) certificate is cheaper and avoids cross-border payment friction but is generally not trusted outside China — so if you ever ship outside the mainland you want a globally trusted CA. Timestamping is mandatory for signature longevity. None of this is documented by any of the frameworks; it is procurement, not engineering.

**Tray / notification.** This is the one place GPUI has a **real gap**:

- **No tray API exists. At all.** `grep -i "tray|Shell_NotifyIcon|NOTIFYICONDATA"` across the whole `crates/` tree returns exactly **one** hit, and it is a comment about `WM_GPUI_FORCE_UPDATE_WINDOW` in `events.rs:1317` — a false positive. There is no notification-area icon type in `gpui`, none in `gpui_windows`, none in `gpui-platform`, and none in `gpui-kit` (the `longbridge/gpui-kit` tree API returns zero paths matching `tray`; the only matches for "notif" are `crates/component/src/notification.rs` — in-app toasts — and `website/docs/system-notification.md`).
- **You must bring `tray-icon` (or `muda`+Win32) yourself.** `tray-icon` 0.26.1, Apache-2.0 OR MIT, 405 stars, last pushed 2026-10-07, is the Tauri-org crate for exactly this and works independently of any UI framework. `muda` 0.21.2 (Apache-2.0 OR MIT) provides native menus. The integration cost is real but bounded: a tray icon means a separate Win32 message-only window and a menu, and you must hand messages back to GPUI's event loop — you cannot put a tray icon inside GPUI's element tree.
- **Notifications work, with a caveat.** `gpui_windows` posts real Windows toasts via `ToastNotificationManager` with a `ToastGeneric` template, title/body and optional action buttons, and routes activation/action clicks back into the app as a `SystemNotificationResponse` — `<CHK>/crates/gpui_windows/src/system_notifications.rs:44-91,157-188`. For an **unpackaged** app it registers `Software\Classes\AppUserModelId\<id>` with a `DisplayName` under HKCU (`<CHK>/crates/gpui_windows/src/system_notifications.rs:190-198`), and **if you never call `App::set_app_identity`, it logs a warning and silently does nothing** ("cannot show a system notification without an app identity; call `App::set_app_identity` during startup") — `<CHK>/crates/gpui_windows/src/system_notifications.rs:141-147`. Windows toast visibility also depends on the user's notification settings, and `show_system_notification` returns `()`, not a delivery result — so a missing toast is not proof of anything ([gpui-kit system-notification docs](https://github.com/longbridge/gpui-kit/blob/main/website/docs/system-notification.md)). For a download manager, "download complete" toasts are exactly the `SystemNotification` use case, and they work — **call `set_app_identity` in `main` before opening any window.**

**Multi-window: pass.** Windows are first-class; the platform keeps a set of HWNDs and the vsync thread invalidates all of them (`<CHK>/crates/gpui_windows/src/platform.rs:472-491`), the frame callback is registered per window (`<CHK>/crates/gpui/src/window.rs:1773-1946`), and moving an entity between windows is a shipped example (`<CHK>/crates/gpui/examples/move_entity_between_windows.rs`).

**DPI: pass, and correctly done.** The embedded manifest declares both `dpiAware=true/pm` (Windows 8.1) and `dpiAwareness=PerMonitorV2` (Windows 10) plus `heapType=SegmentHeap`, requires elevation `asInvoker` with `uiAccess=false`, declares Windows 10 `supportedOS`, and depends on Common-Controls 6.0 — `<CHK>/crates/gpui/resources/windows/gpui.manifest.xml:1-33`. PerMonitorV2 is the right answer for mixed-DPI Chinese laptops-with-external-monitor setups. The manifest is embedded via `embed-resource` unless the host provides one (`windows-manifest-provided-by-host`, which gpui-kit sets) — `<CHK>/crates/gpui/src/fast/windows_manifest.rs:1-14`, `<CHK>/crates/gpui/build.rs:25-28`. A window-scale-factor path exists and is used throughout `gpui_windows` (e.g. IME caret scaling at `<CHK>/crates/gpui_windows/src/events.rs:655-658`). Recent upstream DPI fixes are visible in Zed's release notes ("Fixed the Settings window opening with its header off-screen at high DPI scaling on Windows", #62073).

**Accessibility: pass, with a documented caveat.** `accesskit` 0.24 and `accesskit_windows` 0.34 are dependencies of both `gpui` and `gpui_windows` (`<CHK>/Cargo.toml:86-89`, `<CHK>/crates/gpui_windows/Cargo.toml`), and the Windows window wires an AccessKit adapter into activation handling (`<CHK>/crates/gpui_windows/src/events.rs:803-814`). There is a shipped a11y example (`<CHK>/crates/gpui/examples/a11y.rs`). gpui-kit claims AccessKit roles/names/states/relationships/actions are built into the interaction layer and covered by tests. **The caveat is a Retained Mode interaction**: retention is disabled while accessibility is active — *"Nothing is drawn from the last frame while the window is being refreshed, while something is dragged, while the inspector is picking, or while accessibility is active"* — `<CHK>/docs/retained-mode.md:54-57`. That is a correctness-first choice (a screen reader must see current state) and it means a screen-reader user gets upstream GPUI's frame cost, not gpui-fast's. Also worth knowing: egui has a matching open issue where an occluded/minimized window never answers AccessKit (egui #8671), so this is a general difficulty, not a GPUI-specific one.

**Menus, dialogs, file pickers: pass.** `set_menus` example and Windows dialog/file-picker code exist (`<CHK>/crates/gpui_windows/src/dialog.rs`, `crates/gpui/examples/set_menus.rs`), and gpui-kit ships styled and native menus including `crates/component/src/native_menu/windows.rs`.

### Notes on the two columns people usually get wrong

**Idle cost is not a framework property, it is a repaint-policy property.** egui's author documents the good policy in prose and it is the only project in this table that does. GPUI's policy is equally event-driven but with a permanently-running vsync thread and a retained GPU context. A Win32 app is trivially zero. Everything else is undocumented, which means: **for your tray-for-hours requirement, only egui's claim and Win32's structure are currently supported by published reasoning; GPUI's is supported by source-reading (this report).**

**GPU compatibility is the axis where GPUI wins and wgpu-based frameworks lose.** wgpu supports Vulkan/DX12/GL3.3+ on Windows and **no D3D11** ([wgpu README](https://github.com/gfx-rs/wgpu)). GPUI asks for D3D11 FL10.1 + SM4.x structured buffers — hardware from 2011–2012. For a Chinese install base with a long tail of old Intel iGPUs, that is a materially larger addressable population than DX12/Vulkan-only. iced's `tiny_skia` software renderer and slint's `software` renderer are the other escape hatches, and **GPUI has none**.

## 4. Recommendation

**Recommendation: do not make GPUI/gpui-fast the foundation. Build on plain Win32/Direct2D+DirectWrite (`windows-rs`), or — if you want a framework and can accept a webview — Tauri v2. If you specifically want a GPU-rendered, Rust-native, non-webview UI, then gpui-fast + gpui-kit is the best-looking and fastest-scrolling option available, but it must be adopted as a *vendored, rev-pinned dependency you own*, not as a library you track.**

Reasoning, in the order the requirements bite:

1. **The distribution risk is not hypothetical and it is not small.** GPUI went 315+ days between crates.io releases; a community mirror was rejected; a maintainer republished Zed's crates himself; the component library pins an *exact* snapshot because a caret range previously broke compilation (`longbridge/gpui-kit` Cargo.toml, issue #3156); snapshots ship weekly; `gpui-fast` went 0.1.0→0.1.6 in four days and has two dominant committers. Over a 1–2 year product lifetime you would be re-pinning roughly every 5–7 days of upstream movement or falling behind on Windows IME and DPI fixes. That is a permanent tax on a product whose actual value is in the download engine.

2. **The requirements that matter most are the ones GPUI is weakest on.** Tray support does not exist in GPUI at all — you write it against `tray-icon` and a second Win32 message loop anyway. Idle cost is undocumented and structurally includes a forever-running vsync thread plus a retained D3D device; the switch to headless exists but is an application-level workaround, not a designed tray story. On a GPU-less or Basic-Display-Adapter machine the failure mode is a **startup panic**, not a fallback, and there is no software renderer at all.

3. **The requirements GPUI is strongest on are the ones a download manager needs least.** Retained Mode and scroll layers are optimizations for *editor-class* UIs where a large window changes in small places at high frequency. A download manager's list is virtualized to a few dozen visible rows with a handful of them changing per second — which egui's immediate-mode `TableBody::rows`, iced, Win32 or Qt all handle comfortably. The fork's own benchmarks mostly measure scenarios (60 panels × 64 labels, component galleries, streaming quote tables) that are harder than anything a download manager will do.

4. **The 5k–50k-row requirement does not discriminate.** Every option here virtualizes; GPUI's version is the best-engineered, but the margin only matters if you are also rendering an editor.

**Counter-argument, stated fairly.** If the visual bar is "shadcn/ui quality on Windows, GPU-rendered, sub-frame-accurate, no webview, no C++", then GPUI + gpui-component is the *only* option in this table that delivers it — 75+ polished Apache-2.0 components, a real data table, real charts, Chinese i18n, a Chinese-speaking maintainer who ships a commercial product on it and clearly cares about the mainland market, and the broadest GPU compatibility of any GPU-rendered option. The text and IME path is genuinely good. If that aesthetic is the product's differentiator, the risk is payable — *if* you price it correctly: vendor the fork, own the rebase, and budget engineering time for the tray, the GPU preflight, and the candidate-window fix.

**Cheapest path to a decision: don't decide yet.** The single highest-information, lowest-cost move is a timeboxed spike that measures the four unknowns this report could not resolve from any source: cold start, idle cost, memory at 50k rows, and a real Chinese IME in a real field. Details below.

### 4.1 Risks that would change this recommendation

**Risks that would move me *toward* GPUI/gpui-fast:**

- **R1. Zed ships an official, automated crates.io pipeline with a stability policy.** If `gpui` starts receiving regular releases with a documented compatibility story, the entire §2.5 objection evaporates. Watch: `crates.io/api/v1/crates/gpui` `updated_at` moving past 2025-10-22, and whether versions start tracking Zed releases. This is Zed's stated intent ("we will start working on infra to automatically publish GPUI releases by the end of the month", [gpui-archipelago](https://gpui-archipelago.github.io/news/315-day-vacuum/)) — **verifiably not yet delivered as of 2026-10-12.**
- **R2. A minimal GPUI app cold-starts in well under 300 ms and idles at ~0 % CPU with no measurable battery effect.** If measurement E1+E2 come back clean, the technical case for GPUI becomes strong and only the distribution risk remains.
- **R3. Zed's persistent view tree (#63800) merges to `main` and gpui-fast either converges with it or is superseded by an upstream feature you can consume directly.** That converts "depend on a two-person fork" into "depend on upstream", which is the whole game.
- **R4. The WebView2 preinstall situation in mainland China turns out to be materially worse than assumed** (e.g. a meaningful share of installs on stripped/LTSC/Ghost images without WebView2, or with WebView2 blocked/updated by security software). That would eliminate Tauri as the pragmatic answer and push toward native rendering, which favours GPUI or Win32.
- **R5. You need 120 Hz+ smoothness or GPU-composited scrolling as a visible product feature** (e.g. a live speed-graph-heavy "downloads" view that must never hitch). GPUI's tile compositing is a genuine advantage there.

**Risks that would move me *away* from GPUI:**

- **R6. The spike shows cold start materially above 300 ms.** DirectWrite `GetSystemFontCollection(..., true)` plus D3D11 device creation are both synchronous in platform construction; on an old i3 with a cold font cache this could plausibly blow the budget. This is the most likely way GPUI fails a hard requirement.
- **R7. The vsync thread's continuous `DwmFlush` + `RedrawWindow` shows up as measurable battery drain or prevents package C-state residency over hours in tray.** Laptops are the dominant form factor in this market; a download manager that costs battery while idle is a bad product regardless of how fast it renders.
- **R8. IME candidate-window misplacement (#64850) is judged unacceptable by the target users.** A download manager has few text fields, but "add URL" and "rename file" are *the* interactions, and Chinese users composing Pinyin into a URL/filename field are the primary persona. If the composition text is obscured by the candidate window in the field's actual screen position, that is a visible quality defect in the primary workflow. Fixing it means patching `gpui_windows/src/events.rs` yourself — which means owning a fork, which you already decided to do or not do.
- **R9. You need the app to run on machines where DirectX 11 is unavailable** (Basic Display Adapter, some VMs/RDP configurations, hardened enterprise desktops). GPUI panics; there is no fallback. If the support burden of that is real, only iced (`tiny_skia`), slint (`software`) or Win32/GDI can absorb it.
- **R10. Binary size turns out to matter for distribution in this market** (e.g. you must fit a bundle under a Chinese CDN/网盘 size limit, or ship inside another installer). Zed's Windows installer is 80 MiB, which is an upper bound, not an estimate — but if your ceiling is, say, 15 MB and a spike shows GPUI+gpui-kit lands above it, that is decisive.
- **R11. gpui-fast's upstream sync stalls.** It is five days behind today with a Taffy 0.13→0.14 pin divergence already carried. If sync commits stop appearing in `longbridge/gpui-fast` for more than ~4–6 weeks, or if `script/check-upstream` starts accumulating allowlist exceptions, the fork is decaying and the risk profile changes from "manageable" to "abandoned".
- **R12. Longbridge's priorities move.** Two people carry `gpui-fast` (sunli829 63 commits, huacnlee 32) and one person carries `gpui-kit` (huacnlee 1,473 commits). Corporate-backed open source with a single dominant author is a concentration risk; if Longbridge Pro's needs and yours diverge, you inherit the maintenance.

### 4.2 The cheapest experiment that would falsify the recommendation

**Run one spike, in this order, and stop at the first hard failure.** Total budget: ~3 days of one engineer. It produces the four numbers no public source has.

**E1 — Cold start (half a day).** Build `gpui` examples/`hello_world.rs` and, separately, a `gpui-kit`-based window with a `data_table` of 50k rows, both `--release`, on the *lowest-spec target machine you can get* (an old Intel i3/i5 with integrated graphics and a spinning disk or eMMC, matching the tail of the Chinese install base, not your dev box). Instrument `main` to timestamp process start and take a screenshot-based or in-app timestamp at first presented frame. Measure **both** warm-cache and, critically, **cold** (drop the font cache / reboot or use a fresh VM snapshot) — the DirectWrite `GetSystemFontCollection(checkForUpdates = true)` call in `<CHK>/crates/gpui_windows/src/direct_write.rs:200` is the suspected cost.
**Falsifies if:** cold-start-to-first-paint > 300 ms on the low-spec target. That is a hard requirement and the recommendation flips to Win32 or Tauri without further work.

**E2 — Idle cost in tray (half a day, mostly waiting).** Run the same binary, hide the window, and leave it for **4 hours** on battery on the low-spec laptop. Log, every 30 s: process CPU time (`GetProcessTimes`), working set, and on the machine level `powercfg /energy` output plus `powercfg /batteryreport` before/after. Compare against the same 4 hours with the binary's window hidden and the process suspended, and against a Tauri window hidden to tray.
**Falsifies if:** measurable battery percentage loss attributable to the idle process, or the process shows non-trivial accumulated CPU over 4 hours. Also measure the same thing after calling `App::request_windowing(WindowingRequest::Headless)` when hiding — if headless-on-hide removes the cost entirely, R7 downgrades from "risk" to "one line of application code".

**E3 — Memory at 5k/50k rows (1 hour).** Same binary, tables of 5k and 50k rows, scrolling. Sample private working set and `GPU Process Memory` / `Dedicated GPU memory` from Task Manager or `Get-Counter`. The 64 MiB tile budget (`<CHK>/crates/gpui/src/fast/layers/policy.rs:57`) is per window and is the number to watch. Note that the fork's own memory sampler returns `None` on Windows (`<CHK>/crates/gpui_perf/src/showcase/metrics.rs:390-393`), so use an external sampler.
**Falsifies if:** 50k rows costs materially more than 5k (which would mean rows are leaking into retained state) or the total exceeds your product budget.

**E4 — Chinese IME in the real workflow (1 day, the highest-value test).** Take the built spike, add one text field at the top of a window and one inline rename field inside a scrolled list near the bottom edge of the screen, and drive both with **all three IMEs your users actually use: Microsoft Pinyin, Sogou, and Rime/Weasel**. Test: composition, commit, candidate window position (including when the field is near the bottom edge — issue #64850's exact trigger), backspace during pre-edit (#39608's exact trigger), switching IME mid-composition, and typing into a list row whose hover state changes. Repeat on Windows 10 (1903/22H2) and Windows 11, at 100 % and 150 % DPI.
**Falsifies if:** candidate window obscures composition text in the inline-rename field, or any of the three IMEs fails to commit — the requirement is that Chinese input is a *primary* interaction, so a visible defect here is disqualifying and would need the `CFS_EXCLUDE`/caret-rect fix in `<CHK>/crates/gpui_windows/src/events.rs:655-697` before shipping.

**E5 — Run the same E1–E4 on the runner-up (1 day).** Build the identical UI (task list, progress, speed graph, settings, tray) in the runner-up — Tauri v2 if you are willing to use a webview, Win32+Direct2D if not — and measure the same four things. **Any option whose E1–E4 all pass and whose §2.5-style risk profile is better wins on risk-adjusted terms**, regardless of which one renders prettier. Do not skip this: the whole reason to run E1–E4 is that they are cheap *relative to rewriting the UI later*, and a two-way comparison is barely more expensive than a one-way one.

**Where the spike should live:** as a throwaway crate inside `E:\dsh-workspace\tdmfast` (e.g. `E:\dsh-workspace\tdmfast\gpui-spike\`), never inside the clean-room directories. The spike reads the framework, writes no product code, and can be deleted.

### 4.3 If you adopt GPUI anyway: the minimum-risk configuration

If E1–E4 pass and you decide the aesthetic is worth it, adopt it this way and not any other:

1. **Pin `gpui-fast` to a git rev**, not to crates.io, and vendor it: `git subtree`/`git submodule` into your repo at a specific commit, with your own fork as the remote. Do not use `cargo`'s git dependency for a 1–2 year product — you want the code in your repo, reviewable and patchable.
2. **Do not enable `gpui-kit`'s `gpui-fast` feature**, and do not rely on `[patch.crates-io]` silently applying (`<CHK>/compat/README.md:26-28`). Take `gpui-fast` directly, or take the compat crates as *path* dependencies so a missing patch is a compile error rather than a silent fallback to the upstream snapshot.
3. **Write your UI against `gpui-base` + your own components, not `gpui-component`'s full styled layer**, unless you have validated that its per-frame global writes do not defeat retention. The fork documents that GPUI Kit's `sync_focused_input_registry` / `GlobalState` / `SelectionStateRegistry` writes window-wide state during render and "rebuilds the ancestor views on every scrolled frame" (`<CHK>/docs/scroll-layers.md:170-173`) — i.e. the component library partially cancels the fork's main feature. Verify with `GPUI_VIEW_RETENTION=0` A/B before adopting it wholesale.
4. **Ship a GPU preflight.** Before creating the GPUI application, create a throwaway D3D11 device at FL10_1 and check the `ComputeShaders_Plus_RawAndStructuredBuffers_Via_Shader_4_x` feature flag (`<CHK>/crates/gpui_windows/src/directx_devices.rs:174-193`). If it fails, show a **native Win32/GDI** window explaining the requirement, instead of letting `<CHK>/crates/gpui_windows/src/platform.rs:406` panic. This is a day of work that converts a crash-on-launch into a supportable error state.
5. **Call `App::set_app_identity(id, "Name")` before opening any window** or system notifications silently no-op (`<CHK>/crates/gpui_windows/src/system_notifications.rs:141-147`).
6. **Own the tray** with `tray-icon` (Apache-2.0 OR MIT) and, if you want to drop the GPU while hidden, call `App::request_windowing(WindowingRequest::Headless)` on hide and `Windowed` before showing.
7. **Carry the IME candidate-window fix yourself** (the `CFS_EXCLUDE` + caret-rect change described in [#64850](https://github.com/zed-industries/zed/issues/64850)) rather than waiting for it, and upstream it if you can. It is a small, self-contained patch in `gpui_windows/src/events.rs`, and for a Chinese-market product it is not optional polish.
8. **Instrument the sync cadence.** A CI job that records the pinned commit and the current `longbridge/gpui-fast` HEAD's age, and fails (or at least shouts) past ~6 weeks, turns R11 from a surprise into a signal.

## 5. Things I could not determine, and did not invent

Stated plainly so nobody downstream mistakes silence for a measurement:

1. **Cold start to first painted window for any GPUI app**, on any hardware. Not published by Zed, Longbridge, or the fork.
2. **Idle CPU/GPU/battery cost of GPUI with a window hidden or minimized.** The *mechanism* is fully readable from source (this report, §2.2b); the *number* does not exist publicly. Same for every alternative except egui's qualitative claim.
3. **Resident memory for a GPUI app with 5k–50k rows on Windows.** The fork's own sampler returns `None` on Windows by construction.
4. **Binary size of a minimal GPUI/gpui-kit app on Windows.** Only Zed's full 80.1 MiB installer exists as a (much too high) bound.
5. **Tile-texture memory actually consumed at runtime** — the 64 MiB figure is a budget constant, not a measurement.
6. **Whether `gpui-kit`/`gpui-component`'s per-frame global writes measurably defeat Retention** in a typical app. The fork documents that they do in GPUI Kit's own component gallery; the magnitude in *your* screens is unknown.
7. **WebView2 preinstall coverage on the Chinese Windows install base.** No authoritative figure found. This is load-bearing for the Tauri recommendation and should be treated as an open question, not an assumption.
8. **Whether Zed's automated crates.io pipeline has actually shipped anything.** Zed committed to it publicly and `gpui-pre` 0.3.9 (2026-10-12, huacnlee) is still newer than any official `gpui` publication (0.2.2, 2025-10-22). It may exist in CI without a release having cut yet; I can only report what crates.io shows.
9. **The upstream zed commit `a1b71072e5` could not be fetched from GitHub** (404 on that raw URL, likely a squashed/force-pushed history) — its date and subject were obtained from the commits API instead (2026-10-05, "Remove nix version from Cargo.lock dependency reference (#65206)").
10. **Licensing detail worth a lawyer's eye, not mine to decide:** the fork's `LICENSE` is Apache-2.0 carrying "Copyright 2022 - 2025 Zed Industries, Inc. / Copyright 2026 Longbridge", `LICENSE-APACHE` is a one-line file containing the text `LICENSE`, there is **no `NOTICE` file** anywhere in the tree, and source files carry **no Apache license headers** (0 of the `.rs` files in the checkout contain "Licensed under the Apache License"). Redistributing binaries of Apache-2.0 code requires giving recipients a copy of the license and retaining attribution notices; with no NOTICE file, §4(d) has nothing to carry. The practical obligation for an MIT product is to ship the Apache-2.0 text and a third-party attribution list — but confirm the GPL-3.0 question specifically: Zed's *editor* is GPL-3.0 for some components, and the checkout contains **no `LICENSE-GPL`** and declares Apache-2.0 in every published crate's metadata, which is the strongest available evidence that the GPUI crates are Apache-2.0-only. Verify against the exact upstream commit before shipping.
