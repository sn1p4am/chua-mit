## ⚡ 项目状态重大变化：本机开发环境已恢复

旧项目（`../chua`）认定「本机无法编译引擎，只能靠 CI 验证」，并据此把开发循环改成
「推送 → 等 3.5 分钟 → 从 `ci-status` 分支取结果」。

**这个结论是错的。** 真因是 `%TEMP%` 上的外来 ACL 条目导致 `cl.exe` 无法创建中间文件
（详见 `.omp/PITFALLS.md` **P-001**）。把 `TMP`/`TEMP` 指向工作区内目录后：

| 构建 | 耗时 |
|---|---|
| 完整 GPUI 依赖树，debug | **41 s** |
| 完整 GPUI 依赖树，release | **59 s** |
| 增量 rebuild（改一个文件） | **1.7 s** |

**影响**：M1 起不再需要 CI 往返。CI 只用于"另一台机器/另一个平台也过"的交叉验证。
这是本项目可用性的最大改善。

#### 性能基线（2026-10-12，规格侧实测）

i9-13900K / 64 GB / Windows，**debug** 构建，本地 loopback，1 GiB 单文件、8 段：

| 指标 | 实测 |
|---|---|
| 墙钟 | 40.80 s |
| 吞吐 | **25.1 MiB/s** |
| CPU | 21.00 s（**51% 单核**） |
| **峰值工作集** | **17 MiB** |
| 结果 | 1,073,741,824 字节，SHA-256 逐位一致 |

**两条读数**：

1. **§12「每段内存与文件大小无关」得到证实**：1 GiB 文件、8 段并发，峰值工作集只有 **17 MiB**。
   这条是 M1 验收里唯一可量化的资源约束，现在是观测值而非推断。
2. **25.1 MiB/s 不是引擎的上限，是测试环境的读数。** 判据是客户端**没有跑满**——
   只用了 51% 单核、17 MiB 内存。瓶颈在别处（Python 测试服务器或 loopback），
   不在被测客户端。因此这一项**不能**用来判定「8 段并发是否跑满链路」（标准 2）；
   那需要一个更快的服务端或另一种测量方式，属未完成项。
   另外这是 **debug 构建**；release 下的数字会不同，基线应在补齐标准 2 时一并重测。

| 用例 | 现象 | 归属 |
|---|---|---|

**这是本项目最重要的一个结论**：129 个单元测试全绿，而最基础的操作
——「多段下载一个文件」—— 根本完不成。单元测试覆盖了状态机、区间校验、durable 语义，

`Queued`（调度不发放槽位）／`Downloading` 且某段为 0（`JoinSet` 未排空，

### 验证陷阱（会再踩，务必先读）

1. **`cargo build` 不编译测试目标。** 只跑 `cargo build` 或 `cargo check --lib` 会漏掉

   门禁必须用 `--all-targets`。见 `.omp/PITFALLS.md` **P-004**。
2. **`cargo test --no-run` 失败时，磁盘上的测试二进制是陈旧的**，跑它得到的结论与当前代码无关。
   顺序永远是：先 `--no-run` 成功，再跑测试。
3. **测试空转时不要重跑，用 `--test-threads=1`** 定位（最后打印的测试名就是卡住的那个），
   然后 `--exact <名字>` 单独跑。
4. **批量改写源码不要用 `Get-Content | Set-Content` 往返**，会破坏 UTF-8。见 **P-005**。
   另外：终端里看到中文乱码**不能**证明文件坏了，要用码点检查。

### 验收工具已就绪

`spec/acceptance/`（服务器 7 种模式 + 6 项检查）已**双向自测**：
对一个粗心的多段下载器 `range-ignored` 会失败（证明检查抓得住静默损坏），
对一个守规矩的实现 6/6 通过（证明它不误杀）。**只跑后者是没有意义的**——
它无法区分"实现正确"与"检查形同虚设"。

对真实 CLI 的实测结果：**6/6 通过**。`range-ignored` 走的是 v1.0.4 的第二条路径——
引擎识别出服务器无视了 Range，于是降级为整文件下载，最终字节正确。

### 规格侧本轮的自我修正（累计六处）

实现侧的失败测试与记录逐次暴露了规格缺陷，均已升版并写明起因：

| 版本 | 缺口 |
|---|---|
| v1.0.1 | §4.2「去掉路径分隔符」留下两种读法（取末段 vs 拼接） |
| v1.0.2 | §4.2 未规定解码与取末段的**先后**——顺序反了 `%2F` 可绕过防线 |
| v1.0.3 | §9.1 只说了"要限速"，没说"什么算对"（实现四次重写皆失败） |
| v1.0.4 | §6.3 约束的是结果还是手段（测试断言过严） |
| v1.0.5 | 一次补齐六处：`{Completed,Failed}→Removed`、`Paused→Failed`、未知长度的完成判定、下限优先于对齐、不变式 5 优先于 2、`restore` 后谁重新启动 |

**规律很清楚：我写规格时倾向于写「不要做什么」，而实现需要的是「什么算对」。**
其中五处的形态完全相同——负面清单式的措辞留下了另一种合法读法，
而那种读法会让功能**完全不可用**（已完成的任务无法删除、未知长度模式永远下不完）。
**这是 §4.5 流程按设计工作的证据**：失败测试就是缺口报告，比凭想象写规格准得多。
