# chua 引擎行为规格

**版本**：1.0.5
**状态**：初始版本，覆盖 M1（单源 HTTP 核心）；§5 为 M3 预留
**读者**：实现侧会话。**本文件是引擎实现的唯一信息来源。**
**约束**：本文件只描述"要什么"，不描述任何既有实现的"怎么写"。见 [`../CLEANROOM.md`](../CLEANROOM.md) §5。

---

## 0. 阅读约定

- `MUST` / `MUST NOT` / `SHOULD` / `MAY` 按 RFC 2119 语义。
- **宿主**：使用引擎的程序（CLI、桌面 UI、未来的移动端）。
- 本文件中出现的**所有名字都是本规格自行定义的**。实现侧若发现某个命名与任何既有实现雷同，
  **应当改名**——命名撞车本身就是需要回避的风险。
- 本规格不含代码。实现侧不得从任何既有实现反推本规格未写明的东西；有缺口按
  [`../AGENTS.md`](../AGENTS.md) §4.5 提报。

## 1. 职责边界

**引擎负责**：把来源标识变成完整的本地文件，并在整个过程中维护可恢复的状态。

**引擎不负责**：

- 任何用户界面、窗口、托盘、通知
- 面向用户的文案（引擎只上报结构化原因，由宿主翻译）
- 任何图形 / FFI / 宿主框架的类型

**硬约束**：引擎 MUST NOT 依赖任何图形、窗口或平台 UI 库。这保证它可以被无图形环境的
集成测试完整覆盖（M1 验收方式）。

## 2. 核心概念

| 概念 | 含义 |
|---|---|
| **任务** (Task) | 一次用户可见的下载。有唯一 id、来源标识、目标路径、状态 |
| **来源** (Source) | 一个能取到目标文件字节的端点。同一任务的多个来源互为镜像 |
| **分段** (Segment) | 任务内部的字节区间。并发与续传的单位 |
| **探测** (Probe) | 不下载正文、只询问元数据的行为 |
| **快照** (Snapshot) | 引擎对外发布的、关于某任务当前状态的只读数据 |

### 不变式

- **I1 区间完整**：一个任务的全部活跃分段，其字节区间之并恰好等于 `[0, total_len)`，两两不重叠。
- **I2 长度恒定**：`total_len` 一旦确定，任务生命周期内 MUST NOT 改变。来源给出不同长度时，
  按 §5 处理，**不得就地修改已有任务的长度**。
- **I3 用户数据不可擅动**：引擎 MUST NOT 在未收到宿主显式指令时删除或截断用户可见的数据文件。
- **I4 凭据不外流**：带凭据的请求 MUST NOT 被发往该凭据未授权的主机（§5.4）。
- **I5 单源退化**：只有一个来源时，行为与本规格的多源路径**逐字节等价**。

## 3. 任务模型与状态机

### 3.1 状态

| 状态 | 含义 | 终态 |
|---|---|---|
| `Created` | 已登记，尚未探测 | 否 |
| `Probing` | 正在询问元数据 | 否 |
| `Queued` | 元数据就绪，等待并发位 | 否 |
| `Downloading` | 正在传输字节 | 否 |
| `Paused` | 用户暂停；**可持久化**，重启后仍为 Paused | 否 |
| `Verifying` | 字节就绪，正在校验 | 否 |
| `Completed` | 完成 | **是** |
| `Failed` | 致命失败 | **是** |
| `Removed` | 用户删除 | **是** |

终态 MUST NOT 自动离开。`Failed` 任务可以被宿主的显式「重试」指令重新推进到 `Probing`——
这是一次**显式迁移**，不是终态的自动离开。

### 3.2 合法迁移

```
Created      → Probing                     start
Probing      → Queued                     探测成功
Probing      → Failed                     探测失败且不可重试
Queued       → Downloading                获得并发位
Queued       → Paused                     pause
Downloading  → Paused                     pause
Downloading  → Queued                     让出并发位（被抢占或分段耗尽重排队）
Paused       → Queued                     resume
Downloading  → Verifying                  全部字节就绪 且 启用校验
Downloading  → Completed                  全部字节就绪 且 未启用校验
Verifying    → Completed                  校验通过
Verifying    → Failed                     校验失败
{Probing,Queued,Downloading} → Failed     致命错误（§8）
Paused       → Failed                     致命错误（见下）
非终态        → Removed                   remove
{Completed,Failed} → Removed              remove（见下）
Failed       → Probing                    显式 retry
```

**关于 `Removed`（v1.0.5 补）**：上表原先把 `Removed` 限制在非终态，照字面读就是
**已完成或已失败的任务永远无法删除**——而用户最想清理的恰恰是这些。
§3.1 那句「终态 MUST NOT 自动离开」约束的是**自动**迁移；宿主显式下达的 `remove`
不属于自动迁移，与表中已有的 `Failed → Probing`（显式 retry）是同一形态。故补上这两条边。

**关于 `Paused → Failed`（v1.0.5 补）**：暂停中的任务没有 worker 在跑，因此不存在
「运行中出错」这条路径。但**外部原因**仍可让它失败——校验和失败、目标文件被外部删除、
磁盘满在恢复时才被发现。故允许该边，且它 MUST 只由**引擎可观测的具体原因**触发，
MUST NOT 被用作「暂停超时」之类的兜底。

**非法迁移 MUST 返回明确错误，MUST NOT 静默忽略。**

### 3.3 任务快照字段

引擎对外发布的每个任务快照 MUST 至少包含：

| 字段 | 语义 |
|---|---|
| `id` | 本地唯一标识，进程重启后不变 |
| `state` | §3.1 的状态 |
| `source_label` | 来源标识（下载地址或等价物），原样保存 |
| `target_path` | 最终文件路径 |
| `total_len` | 总字节数；未知时为「未知」而不是 0 |
| `done_len` | 已确认落盘的字节数（**不是**已收到的字节数） |
| `segments` | 分段列表：区间、各自进度、当前绑定的来源 |
| `rate_bps` | 当前速率（§9.4） |
| `eta_secs` | 预计剩余秒数；无法估计时为「未知」 |
| `fail_reason` | 失败时的结构化原因（§8） |
| `created_at` / `updated_at` | 时间戳 |

> `done_len` 的语义是**已落盘**而非**已接收**。这个区分决定了崩溃后进度是否可信，见 §7.3。

## 4. 元数据探测

探测的目的：在下载正文前确定 `total_len`、最终文件名、以及来源是否支持分段。

### 4.1 探测请求的要求

- MUST 使用不会传输正文的方式询问。
- MUST 跟随重定向，并记录**最终**地址；最终地址是后续请求的基准。
- SHOULD 携带 `Range` 请求头以主动探测分段能力，而不是依赖 `Accept-Ranges` 的声明——
  声明与行为不一致的站点很常见，**以实际响应为准**。

### 4.2 从响应中确定的信息

| 信息 | 来源 | 缺失时的处理 |
|---|---|---|
| 总长度 | 内容长度头，或范围响应的总长度字段 | 进入**未知长度模式**（§4.3） |
| 是否支持分段 | 是否返回了范围响应 | 不支持则单段下载 |
| 最终文件名 | 内容处置头 → 最终 URL 路径 → 宿主提供的名字 | 按此顺序取第一个可用值 |
| 强验证器 | 实体标签（非弱标记） | 无 |
| 弱验证器 | 实体标签（弱标记）或最后修改时间 | 无 |

**文件名解析 MUST 处理**：百分号编码、RFC 5987 形式的编码文件名、路径末段与查询串的分离。

**路径分隔符 MUST 按「取末段」处理，不得按「删掉分隔符后拼接」处理。** 即：一个含有路径的候选名
先取最后一个非空路径段，再做净化。`/etc/passwd` → `passwd`，`..\..\x.txt` → `x.txt`，
`a/b/c.zip` → `c.zip`。

**三个步骤的顺序是硬性的**：先**解码**（百分号解码、RFC 5987 解码）→ 再**取末段** → 最后**净化**。

> 澄清（v1.0.2）：顺序反了会漏掉**编码形态的分隔符**。`%2F` 与 `%5C` 解码后就是路径分隔符，
> 若在解码前取末段，`a%2Fb.txt` 会被当成一个不含分隔符的名字，解码后得到 `a/b.txt` ——
> 一个字面斜杠就被带进了文件名。反过来，先把 `%E6%96%87%E4%BB%B6%20name.zip` 解码成
> `文件 name.zip`，再取末段，结果才是 `文件 name.zip`。
> **解码必须发生在分隔符判定之前**，否则这道防线形同虚设。

> 澄清（v1.0.1）：初版只写了"去掉路径分隔符"，这留下了两种读法。拼接读法会得到
> `etcpasswd` 这类**与原意不同的名字**——用户看到的是一个不存在的文件名，而 `..` 被吃掉后
> 剩下的内容仍然留在名字里。取末段才是"这个文件叫什么"的本意，也让 `..` 完全消失。
> 两种读法在安全性上都能挡住穿越（净化后的名字不含分隔符），差别在正确性，所以这条是 MUST。

解析结果 MUST 再经过净化：去掉残留的路径分隔符、控制字符、Windows 保留名（`CON`、`PRN`、`AUX`、
`NUL`、`COM1`–`COM9`、`LPT1`–`LPT9`，且大小写与扩展名无关）、结尾的点与空格。
净化后为空的名字 MUST 由调用方回退到别的候选来源，MUST NOT 使用空名。

### 4.3 未知长度模式

`total_len` 未知时：MUST 退化为**单段顺序下载**；MUST NOT 尝试分段；
进度以「已下载字节数」呈现，MUST NOT 显示百分比。
若来源在中途给出了长度（例如收到内容范围响应），MAY 切换到已知长度模式并重新分段，
但 MUST NOT 丢弃已写入的字节。

**如何判定「下完了」（v1.0.5 补）**：未知长度模式下，传输的结束由**来源关闭连接**表示——
接收到干净的 EOF 即该段完成。**MUST NOT 把 EOF 当作「响应被截断」**：在没有声明长度的
前提下，EOF 就是唯一的结束信号，把它当错误会让这个模式**永远无法完成**
（实现侧最初正是如此：未知长度模式下任务永不进入终态）。

收到 EOF 时，引擎 MUST 把**实际收到的字节数**作为该任务的 `total_len` 落库
（这落在本节的「来源在中途给出了长度」范围内——长度是观测到的，不是声明的），
并使任务进入 `Completed`。

**与 §6.3 的边界**：声明了长度却提前断开，是「响应被截断」，属可重试失败（§8.2 数据不一致）；
**没有**声明长度而断开，是正常结束。两者的区分依据是**响应是否声明过长度**，
不是「收到多少字节」。

### 4.4 探测失败

探测失败 MUST 按 §8 分类。可重试的失败 MUST 退避重试（§8.3），不可重试的直接进 `Failed`。
探测 MUST 有总时限；超时视为可重试失败。

## 5. 多来源与一致性

> 本节是 M3 的行为规格。M1 只有一个来源，实现时可以只做「单来源」这条路径，但
> **接口形状必须容纳本节**，否则 M3 会返工。

### 5.1 来源集合

一个任务可以绑定多个来源。每个来源有：标识、下载地址、优先级。

来源集合的来源（按优先级）：宿主显式提供 > 规则库匹配 > 单一来源。

### 5.2 一致性判据

多个来源只有在**被判定为同一文件**时才允许合并计数与分担分段。

**判定 MUST 基于以下证据组合**：

| 证据 | 是否充分 |
|---|---|
| 总长度一致 **且** 强验证器一致 | ✅ 同一文件 |
| 总长度一致 **且** 强验证器均缺失，弱验证器一致 | ⚠️ 视为同一文件，但 MUST 在任务上标记「未强校验」 |
| 仅总长度一致 | ❌ **不充分**，MUST NOT 合并 |
| 长度不一致 | ❌ 不同文件 |
| 强验证器冲突 | ❌ 不同文件 |

**明确禁止**：不得以「传输层安全」「域名可信」「响应头相似」作为同一性的证据。
这些与内容同一性无关。

### 5.3 加权分配

分段在来源之间的分配 MUST 满足：

1. 初始分配按来源优先级与配置权重。
2. 运行期允许调整：观测到某来源明显慢于其他来源时，SHOULD 把待分配的分段让给更快的来源。
3. 已经分配给某来源且已有进度的分段，MUST NOT 因调整而丢弃其进度。
4. 分配结果 MUST 可解释——每个分段在任一时刻都能回答「为什么是这个来源」。
5. 全部来源都不可用时，任务进 `Failed` 而不是永久等待。

### 5.4 凭据边界

- 若某来源的地址带有凭据（签名参数、Cookie、授权头），该请求 MUST 只发往该来源的原始主机。
- **MUST NOT** 把带凭据的请求改写到其他主机，即使规则库里有对应镜像。
- 规则改写导致主机变化时，MUST 先剥离凭据再发出，或直接不使用该镜像。
- 这条规则是硬的：违反属于安全缺陷，不是「尽力而为」。

### 5.5 来源健康度

引擎 SHOULD 记录每个来源的运行表现（成功率、平均速率）。

- 健康度**只衰减、不提升**（一次成功不足以抹掉多次失败），除非有明确的恢复信号。
- **未知来源 MUST NOT 被惩罚**——没有数据不等于数据差。
- 健康度 MUST 有下限，MUST NOT 让一个来源被永久放逐。
- 健康度只影响分配权重，MUST NOT 单独决定任务的成败。

## 6. 分段下载

### 6.1 分段规则

- 分段数 MUST 有上限，且上限可配置；超过硬上限的配置值 MUST 被拒绝而不是静默截断。
- 分段边界 SHOULD 对齐到可配置的粒度，避免产生大量极小的分段。
- 单段 MUST NOT 小于一个下限（例如 1 MiB），否则调度开销超过收益。
- 长度小于阈值（例如 4 MiB）的文件 SHOULD 只用一个分段。

**下限优先于对齐（v1.0.5 补）**：对齐是 SHOULD，下限是 MUST，冲突时下限胜出。
候选边界若会产生小于下限的分段，MUST 舍弃该边界并把它的字节并入前一段；
文件末尾的余段同样受下限约束，MUST NOT 产生「若干正常段 + 一个几字节的尾巴」。
实现侧最初按对齐规则切分，为 8 MiB 的文件产生了 3 个 1 字节的分段。

**配置校验 MUST 约束两者的关系**：`granularity` 小于 `min_segment_bytes` 时，
MUST 在配置校验阶段报错，而不是留到切分时才产生退化结果。

### 6.2 动态调整

- 下载中 SHOULD 允许「拆分落后分段」：把一个大分段一分为二，两半并行。
- 拆分 MUST 保持 §I1 的区间不变式。
- 已完成的分段 MUST NOT 被拆分。
- 拆分 SHOULD 有冷却时间，避免抖动。

### 6.3 分段请求

每个分段的每次请求 MUST：

1. 声明自己需要的精确字节区间。
2. 校验响应的区间与总长度是否与请求一致；不一致 MUST 视为该来源不可用（§8）。
3. 全量校验：收到「服务器返回了完整文件而不是区间」这类退化响应时，
   MUST NOT 把它当作区间数据写入——这会静默损坏文件。

**这是最容易被忽略、后果最严重的一类错误。实现 MUST 有专门的处理分支。**

**约束的是结果，不是手段**（v1.0.4 澄清）。上面禁止的是「把整份响应当作区间数据写进去」。
在此前提下，遇到退化响应有两种都合规的处置：

1. **判失败**，把该来源标记为不可用；或
2. **改用整文件下载恢复**——丢弃分段计划，从偏移 0 接收整份响应。

**唯一的硬要求是：退出时若声称成功，磁盘上的字节必须正确。**
「报告完成但文件是错的」是唯一不可接受的组合；
「报告完成且文件正确」与「报告失败」同样合规。

> 澄清起因：实现侧的一个集成测试断言这种情况**必须**返回 `Failed`，
> 而规格只禁止了"当作区间数据写入"，并未要求必须失败。
> 两者都读得通——所以把判据写成对**结果**的要求，而不是对**状态**的要求。

### 6.4 写入

- 分段数据 MUST 写入预分配的、可按偏移寻址的本地文件，MUST NOT 依赖内存缓冲整个分段。
- 写入并发 MUST 受控；同一区间的写入 MUST NOT 交错。
- 每个分段已完成的区间 MUST 被持久化（§7）。

## 7. 持久化与断点续传

### 7.1 持久化的内容

| 内容 | 要求 |
|---|---|
| 任务记录 | 所有 §3.3 字段中非派生的部分 |
| 分段记录 | 区间、已完成区间、绑定来源 |
| 配置 | 见 §11 |
| 来源健康度 | 见 §5.5；允许丢失（是缓存而非事实） |

### 7.2 持久化的时机

- 任务状态变化时 MUST 持久化。
- 分段进度 MUST **周期性**持久化，而不是只在完成时。周期 MUST 可配置，默认值应在
  「崩溃丢进度」与「写盘过于频繁（唤醒机械盘 / 磨损 SSD）」之间取得平衡。
- 落盘 MUST 是原子的（先写临时再替换，或使用事务），MUST NOT 出现半截记录。
- 引擎 MUST 在退出路径上做一次最终落盘，但 MUST NOT 依赖它——崩溃才是常态。

### 7.3 恢复

进程重启后：

1. 所有非终态任务 MUST 被恢复。
2. `Downloading` 状态的任务恢复时 MUST 回到 `Queued`，**不得**直接回到 `Downloading`
   （并发位需要重新分配）。

**谁把它们重新跑起来（v1.0.5 补）**：`restore` 只做**状态归一化**，MUST NOT 自行启动传输。
是否让恢复出来的 `Queued` 任务立即开始，由宿主的显式选择决定（配置项或命令）。
理由是 §3.2 里 `Queued → Queued` 不是合法迁移，宿主没有任何公开接口能"再次开始"一个
已是 `Queued` 的任务 —— 若 `restore` 不启动、宿主也无从启动，恢复出来的任务就成了
**永远卡在 `Queued` 的孤儿**。故规格要求二者之一：`restore` 在宿主选择自动恢复时启动传输，
或提供一个显式的「开始这个已排队任务」的接口。**MUST NOT 两者皆无。**

实现侧的落点：`EngineConfig::auto_resume`（该字段此前存在、有文档、但无任何代码读取）。
3. **已落盘字节的信任规则**：`done_len` MUST 只统计「已持久化确认」的字节。
   崩溃前已接收但未持久化的字节 MUST 被重新下载。宁可重下，不可错位。
4. 目标文件已存在且长度与 `total_len` 一致时，MUST 先按 §7.4 处置，MUST NOT 直接覆盖。
5. 分段记录与目标文件长度不一致时，MUST 以「保守」为准：截断到确认的字节数并重下其余部分。

### 7.4 目标文件冲突

目标路径已存在时，引擎 MUST 上报冲突给宿主并由宿主决定（覆盖 / 改名 / 跳过 / 续传）。
引擎 MUST NOT 自行决定覆盖。

### 7.5 校验

启用校验时，字节全部就绪后 MUST 在 `Verifying` 状态下计算校验值。
校验失败 MUST 进 `Failed` 并携带「期望值 / 实际值」，MUST NOT 自动删除文件。

## 8. 错误分类与重试

### 8.1 分类维度

每个失败 MUST 至少能回答两个问题：

1. **是哪一类**（供宿主翻译成用户能看懂的说明）
2. **能不能重试**（供引擎自己决定）

### 8.2 分类表

| 类别 | 典型触发 | 可重试 |
|---|---|---|
| 来源不存在 | 资源缺失响应 | ❌ |
| 拒绝访问 | 鉴权失败响应 | ❌（但签名过期是特例，见下） |
| 被限流 | 请求过多响应；重试等待头给出 | ✅ 且 MUST 尊重服务端给出的等待时间 |
| 签名过期 | 鉴权失败且地址含时效性参数 | ✅ 但 MUST 走**重新获取地址**的路径，而不是原样重试 |
| 网络瞬断 | 连接重置、超时、临时不可达 | ✅ |
| 服务器错误 | 5xx | ✅ |
| 磁盘不足 | 写入失败、空间不足 | ❌（需要用户介入） |
| 磁盘其他错误 | 权限、路径非法 | ❌ |
| 数据不一致 | 区间响应与请求不符、长度变化 | ✅ 但 MUST 换用其他来源或重新探测 |
| 校验失败 | 校验值不符 | ✅ 一次；再失败即终止 |
| 用户取消 | 显式取消 | ❌ |
| 未知 | 其他 | ✅ 有限次 |

### 8.3 退避

- 重试 MUST 指数退避，MUST 有最大次数与最大间隔。
- 被限流时 MUST 优先使用服务端给出的等待时间，而不是自己的退避曲线。
- 退避 MUST 有随机抖动，避免多任务同步重试形成脉冲。
- 重试次数用尽后进 `Failed`，并保留最后一次的具体原因。

### 8.4 归因上报

引擎 MUST 上报结构化原因，**MUST NOT 上报面向用户的文案**。
宿主负责把原因映射成中文说明与建议动作。同一个原因在不同宿主上可以有不同的措辞。

## 9. 速率

### 9.1 限速

- MUST 支持全局限速与单任务限速。
- 两者同时生效时，实际速率取更严格者。
- 限速 MUST NOT 通过「长时间 sleep 再突发」实现——那会造成流量脉冲。
- 限速值的变化 MUST 在运行中生效，不需要重启任务。

**配速机制的不变式**（v1.0.3 补充）：

1. **单一事实源。** 配速只有**一个**地方记录"已经为多少字节付过账"。
   同时维护「令牌余额」与「预留时间线」两套记账是**禁止**的：
   两者会各自推进，并对"已付多少"得出不同的答案，从而必然出现超发或过度限速。
   （实现侧曾在此重写四次，每次都在两个机制之间来回倒——本节就是为此写的。）

2. **上下界。** 连续传输 `N` 字节的墙钟时间 MUST ≥ `N / rate`（不得超发），
   且 SHOULD ≤ `N / rate + 一个分块的时间`（不得过度限速）。
   允许一个分块时间的初始延迟——「先等待后发送」与「先发送后等待」的平均速率相同。

3. **并发不得重复计费。** 并发调用者预留的区间 MUST 两两不重叠。
   总耗时随调用者数量**线性增长**，MUST NOT 因并发而缩短。
   这是 §9.1 里"取更严格者"在多调用者情形下的具体含义。

4. **重试必须有界且单调推进。** 配速计算 MUST NOT 存在无界循环：
   每一次重试都 MUST 观察到**严格更大**的已预留量，否则循环可能原地打转。

5. **改速率不追溯。** 运行中改速率 MUST 只影响之后的预留；
   已经在等待中的调用者保持其既得区间，MUST NOT 被重新计算。

**不变式 2 与 5 的优先关系（v1.0.5 补）**：把速率**调高**时两者会冲突——
不变式 5 要求已发出的预留保持不变，于是那些预留仍按**旧**（较慢）速率记账，
新一次的等待就会长于按新速率算出的 `N / rate`。**不变式 5 优先**（它是 MUST，不变式 2 的上界是 SHOULD）：

- MUST NOT 为追上新速率而缩短已发出的预留（那会破坏不变式 1 的单一事实源）；
- 过度限速 MUST 有界：上界为「每条传输通道一个分块」的量级，MUST NOT 随历史累积放大。

换言之：**调高速率时，已经排队的部分慢一点是允许的，但不允许慢得没有上限。**

> 判据：把上述五条写成断言，它们应当全部可由**不访问私有状态**的公开行为验证——
> 若某条只能靠读内部字段来检查，说明配速的对外语义还不够清楚。

### 9.2 速率测量

- 速率 MUST 使用滑动窗口，而不是「总字节 / 总耗时」（后者会让长任务的速率对近期变化失去反应）。
- 窗口长度 MUST 可配置，默认值应在 3–10 秒量级。

### 9.3 预计剩余时间

`eta_secs` SHOULD 基于滑动窗口速率。
速率过低或波动过大时，MUST 上报「未知」而不是给出一个剧烈跳动的数字。

### 9.4 上报频率

- 速率与进度事件 MUST 有频率上限（默认 10 Hz 量级），MUST NOT 每个数据块都上报。
- 上报 MUST NOT 阻塞传输路径。

## 10. 事件出口

### 10.1 要求

- 引擎向宿主发布事件，MUST NOT 反向依赖宿主的类型。
- 事件 MUST 是自包含的快照或增量，宿主 MUST 能在丢失若干事件后靠重新拉取全量恢复。
- **MUST 提供全量快照的获取方式**——这是宿主界面重建与事件丢失恢复的基础。
- 事件出口 MUST NOT 阻塞引擎的调度循环。

### 10.2 事件种类（至少）

| 事件 | 触发 |
|---|---|
| 任务新增 / 删除 | 任务集合变化 |
| 任务状态变化 | §3.2 的任一迁移 |
| 进度更新 | 周期上报（§9.4） |
| 分段变化 | 分段新增 / 完成 / 重新绑定来源 |
| 失败 | 进 `Failed`，带结构化原因 |
| 队列变化 | 并发位分配变化 |
| 来源变化 | 来源加入 / 移除 / 健康度显著变化（M3） |

## 12. 资源约束

- 单任务内存占用 MUST NOT 随文件大小增长（不得把文件读进内存）。
- 分段进度状态的内存占用 MUST 与分段数成正比，MUST NOT 与已下载字节数成正比。
- 引擎 MUST NOT 在有活动任务时进行与传输无关的周期性磁盘扫描。
- 空闲时（无活动任务）引擎 MUST 保持静默：不做周期性的目录扫描或数据库写入。
