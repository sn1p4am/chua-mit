# 验收套件（spec/acceptance/）

**这一套属于规格侧。** 它定义引擎必须能正确应对的**环境**与必须满足的**外部行为**，
不关心引擎内部怎么实现。引擎被当作**黑盒**驱动 —— 只经它的命令行接口，
不 import 任何引擎代码，因此同一套检查可以拿去验证任何满足 `spec/engine-v1.md` 的实现。

## 为什么它在这里，而不是在 `crates/` 里

`crates/` 下的测试是实现自己的测试：它们知道内部结构，会跟着重构一起改，
也可能和实现共享同一个误解。验收套件要的恰恰是**不共享误解**——
它只从规格出发描述"输入这些请求，磁盘上应该留下什么"。

两者都要有。这是"测了"和"验过了"的区别。

## 怎么跑

```bash
# 先构建 CLI（注意：本机必须先把 TMP/TEMP 指到工作区内，见 .omp/PITFALLS.md P-001）
cargo build --release -p chua-cli

cd spec/acceptance
python run.py --cli ../../target/release/chua-cli
```

只跑服务器、手动观察：

```bash
python range_server.py --port 8731 --size 8388608
# 运行时切换行为：
curl 'http://127.0.0.1:8731/_mode?m=ignore-range'
```

## 核心断言

每一个场景最终都归结为同一句话：

> **要么大声失败，要么磁盘上的字节是对的 —— 绝不能"报告成功而文件是错的"。**

这条比"下载成功"重要得多。一个下载器偶尔失败，用户重试就好；一个下载器**静默写坏文件**
并告诉用户完成了，用户可能要过几个月才发现，而且无从追查。

## 服务器模式

| 模式 | 行为 | 用途 |
|---|---|---|
| `normal` | 正确响应 Range，回 `206` + `Content-Range` | 正常路径 |
| `ignore-range` | **无视 Range，回 `200` + 整份文件** | 最重要的一种。落到偏移 A 就是静默损坏 |
| `no-length` | `200`，无 `Content-Length`，靠关闭连接分帧 | 未知长度降级（规格 §4.3） |
| `short-body` | 声明 `Content-Length` 却只发一半就关连接 | 截断必须被发现 |
| `server-error` | 恒 `500` | 重试后仍失败，且不产生错误产物 |
| `rate-limited` | 恒 `429` + `Retry-After: 1` | 必须尊重服务端给出的等待时间（§8.3） |
| `missing` | 恒 `404` | 不可重试，必须**迅速**失败而不是重试到超时 |

运行时可用 `/_mode?m=<模式>` 切换，用 `/_sha256` 取正确结果，用 `/_requests` 看请求计数。

## 检查清单

| 检查 | 断言 |
|---|---|
| `clean-download` | 8 MiB 多段下载，sha256 与服务端一致 |
| `range-ignored` | **退出码 0 则字节必须正确**；退出码非 0 即算通过（大声失败总是可接受） |
| `unknown-length` | 无 `Content-Length` 时降级为单段顺序下载并完成 |
| `not-found` | 非零退出，且 30 秒内失败（不可重试的错不该耗到超时） |
| `rate-limited` | 不产生错误产物 |
| `resume-after-kill` | 下载中途 `kill`（模拟断电），重启后最终字节仍与服务端一致 |

最后一项是真正会暴露"已落盘 vs 已接收"混淆的地方（规格 §7.3）：
如果实现把**已接收**的字节当作已完成，断电续传后文件就会错位，而平时下载完全正常。

## 套件自身的验证（`fake_cli.py`）

**一个没被证明过能失败的检查，等于没有检查。** 因此本目录有一个刻意的假 CLI
（`fake_cli.py`，**不是产品，切勿混淆**），用来双向验证套件：

```bash
# A) 粗心的多段下载器：对 Range 请求的 200 响应不作校验
python run.py --cli python fake_cli.py
#    期望：range-ignored FAIL ——「CLAIMED SUCCESS (exit 0) with a wrong result」

# B) 守规矩的下载器：实现 §6.3 校验
FAKE_CLI_GUARD=1 python run.py --cli python fake_cli.py
#    期望：6/6 全过
```

**两个方向都必须成立**：A 证明检查抓得住静默损坏，B 证明它不会误杀正确实现。
只跑 B 是没有意义的——它无法区分"实现正确"与"检查形同虚设"。

这个自测确实抓到了套件自身的四个缺陷，包括最要命的一个：
`range-ignored` 原先以**文件大小**判定，于是预分配了正确长度但内容错误的文件被误判为通过，
而一个正确实现（预分配后失败退出）反而会被判为失败。现在判定只看**退出码**——
因为退出码才是下载器"声称成功"的方式。

## 已知的接口假设

套件按 `.omp/ROADMAP.md` 里 M1 的 CLI 形状驱动：`add <url> [dest]`、`resume --all`。
`resume --all` 失败时会回退到重新 `add` 同一 URL（正常实现应当续传而不是重下）。

如果 CLI 的最终形状与此不同，改 `run.py` 的调用处即可 —— **不要**为了迁就套件去改规格，
除非规格本身确实没写清楚（那就按 `AGENTS.md` §4.5 记缺口、升规格版本）。
